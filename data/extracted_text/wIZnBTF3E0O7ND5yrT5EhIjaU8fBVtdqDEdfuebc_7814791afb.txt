INTRODUCTION GÉNÉRALE
General Introduction
Teaching young children has never been a simple task, and the challenge becomes even more
apparent when the subject involves abstract concepts like logic and computational thinking. For
kids between 10 and 14 years old, traditional classroom tools rarely offer the kind of interactivity
that holds their attention long enough to make an impression. This gap, small as it may seem,
has real consequences, a generation growing up in a technology-driven world without early
exposure to the foundations of that world.
Robotics have gradually opened a different path. Rather than replacing the teacher,
interactive robots can sit alongside the learning process, responding to a child’s actions, giving
feedback, and making otherwise dry concepts feel immediate and concrete. The combination
of IoT connectivity, onboard sensing, and AI-driven interaction has made this kind of system
increasingly practical to build, even at a small scale.
This project, EduBot, is an ESP32-based educational robot built for children aged 10 to 14.
Designed as an interactive learning companion with a web application that allows monitoring
and control, tying the hardware and software into a single coherent system.

1.4 Proposed Solution
Based on this comparative study, EduBot is proposed as an interactive educational robot
designed to address the identiﬁed limitations of existing solutions by bringing together
hardware, software, and artiﬁcial intelligence into a single, coherent educational platform.
The robot is based on two main components : an Espressif 32-bit microcontroller family
(ESP32) for control and an ESP32 camera module (ESP32-CAM) for vision. Communication
runs over Wireless Fidelity (Wi-Fi) using Real-time bidirectional communication protocol
(WebSocket), enabling real-time interaction with a web application built with React and
JavaScript runtime environment (Node.js). Through that interface, users can control the robot
and receive instant feedback.
Unlike traditional robots, EduBot includes AI features based on a convolutional neural
network (Convolutional Neural Network (CNN)) model [4] trained to recognize custom sign
cards through the camera module. It also provides an interactive learning environment where
children can program the robot using blocks, draw a path and run it so the robot can follow it,
complete tasks, and answer quizzes. This turns programming into an active, hands-on process.
A separate interface for teachers is also part of the system. It allows educators to design
tasks, create quizzes, and monitor each student’s progress. In that sense, EduBot is more than a
robot — it becomes a full educational platform.

To put Agile into action, we followed the Scrum framework. Scrum is one of the

2.5 System Architecture
The EduBot system operates in two functional modes, selected via a physical switch
connected to the ESP32. Upon initialization, the ESP32 registers its network address and
operational status with Firebase Firestore [24], enabling the mobile application to dynamically
discover and connect to the robot. The ESP32-CAM similarly transmits its network address to
the ESP32, which subsequently relays it to the application as part of its ping response.
2.5.1
Manual Mode
In manual or coding mode, the system operates across three layers. Firebase Authentication
(Firebase Auth) [24] handles all identity management, teachers register and log in through that
service, and students enter the app using a class code. Teachers create and manage classes,
deﬁne custom code blocks, and publish tasks, all of which are written to Firestore. Student
proﬁles, their saved visual programs, and their class assignments are also stored and retrieved
from Firestore.
The web application maintains a continuous two-way relationship with Firebase : it writes
data such as programs, tasks, and task results upward, and receives real-time synchronization
downward via Firestore’s onSnapshot listener, keeping the teacher dashboard and student task
panel always up to date. Once the app retrieves the robot’s network address from Firebase,
all further robot communication bypasses the cloud entirely — the app sends programs and
commands directly to the ESP32 over the local network using dedicated action and data request
endpoints. The ESP32 then interprets these commands and drives the physical hardware —
motors, display, and sensors — accordingly. This design keeps latency low for real-time robot

control while using the cloud only as an authentication, discovery, and data-persistence layer.

2.5.2
Vision-Based Mode
When the physical switch on the robot is ﬂipped to auto mode, the ESP32 detects the state
change and simultaneously triggers two actions. First, it broadcasts a real-time message to the
web application notifying that auto mode is now active. Second, it sends a command to the
ESP32-CAM to start detection, including which model to use.
Upon receiving the auto mode notiﬁcation, the web application immediately requests the
live video stream from the camera module by opening a direct connection to its video feed
endpoint. The camera module responds by continuously pushing video frames back to the
browser, displayed in a full-screen stream overlay. In parallel, the camera module activates
its detection mode, captures frames, encodes them, and sends them over a secure connection to

3.6 Firebase Integration
3.6.1
Real-Time Data Synchronization
To ensure low-latency, consistent data delivery across all connected sessions, the application
adopts a push-based, event-driven synchronization model. Unlike traditional polling-based
approaches, where clients repeatedly query the server at ﬁxed intervals regardless of data
availability, this model pushes updates to all subscribed clients the instant a change occurs,
eliminating unnecessary network overhead and improving responsiveness. To leverage this
capability effectively, the system was designed around a multi-listener architecture, where
distinct listeners are assigned to each functional domain — teacher activity and student
interaction — ensuring that any change propagates immediately to all relevant parties within
those roles. Administrative views, by contrast, retrieve data on demand through one-time reads
rather than maintaining persistent subscriptions.
Page 74


===== PAGE 93 =====

CHAPITRE 3. SPRINT 2 : WEB PLATFORM DEVELOPMENT
3.6.2
Persistent Data Storage
To ensure continuity across sessions and devices, the application employs a persistent
cloud-based storage strategy for all core educational data. Student work is preserved at a
granular level, capturing both the content of each saved project and a record of when it was last
modiﬁed, enabling complete recovery of prior activity at any point in time. Submission records
and performance results are permanently retained upon writing, providing instructors with a
reliable and enduring log of learner progress. Beyond student data, instructor proﬁles, course
conﬁgurations, and all associated resources are stored independently of any active session,
ensuring that the system state remains intact and immediately accessible regardless of when
or where the application is resumed.
3.6.2.1
Robot Device Data
To maintain an up-to-date registry of all physical robot devices, the application
stores device-speciﬁc information in Cloud Firestore. Firestore operates as a NoSQL,
document-oriented database optimized for ﬂexible, schema-free data storage and real-time
access. To leverage these capabilities effectively, a structured document model was designed to
organize all robot-related information under a unique hardware-derived identiﬁer. As illustrated
in the ﬁgure, each robot document is organized into four logical groups : identiﬁcation ﬁelds

access control ﬁeld enforcing exclusive student-to-robot assignment.

Sprint 3 : Vision-Based Mode
Introduction
This chapter details the development and integration of an intelligent autonomous behavior
for the EduBot, introducing an auto mode driven by computer vision. The primary objective
was to enable the robot to recognise physical cards through its onboard camera and react
automatically — executing movement control commands, displaying emotional expressions,
and responding to safety conditions. Beyond technical autonomy, this feature gives young
learners a hands-on way to explore basic AI concepts, encouraging early engagement with
intelligent systems. When the robot can see and respond to a physical card, it transforms from
a simple remote-controlled device into a responsive companion. This kind of interaction not
only makes learning more engaging but also helps children form a stronger bond with the robot,
sustaining exploration and curiosity. Ultimately, this auto mode gives the robot a simple form
of independent decision-making, allowing it to operate on its own and react to what the camera
sees in real time.
Page 80


===== PAGE 99 =====

CHAPITRE 4. SPRINT 3 : VISION-BASED MODE
4.1 Sprint Objectives
The objective of this sprint is to implement the auto mode feature of the EduBot robot,
enabling it to operate autonomously based on real-time visual input rather than student-written
programs. This sprint covers the full detection pipeline : training a Residual Network with 18
layers (ResNet18) classiﬁcation model [32] on a custom card dataset, deploying it on Roboﬂow
[11] for cloud inference, implementing the ESP32-CAM ﬁrmware to capture frames and retrieve
classiﬁcation results, and integrating the detection pipeline with the ESP32 to drive the motors
and trigger audio announcements through the DFPlayer module. On the web application side,
the sprint delivers a full-screen auto mode overlay that displays the live MJPEG camera feed
alongside the detected label and conﬁdence score in real time. The transition between auto mode
and manual coding mode is controlled entirely by a physical switch on the robot, making the
experience intuitive and immediate for young students. By the end of this sprint, the EduBot
robot is capable of recognising a shown card, moving or expressing accordingly, announcing
the appropriate sound aloud, and reﬂecting the result live on the web application — introducing
students to the concept of artiﬁcial intelligence in an interactive and engaging way.

4.2.1
Computer Vision Platform : Roboﬂow
Roboﬂow [33] is an end-to-end computer vision platform that simpliﬁes model training,
dataset management, and model deployment, and provides a hosted inference API accessible
from any HTTP-capable device. In the auto mode sprint, Roboﬂow was used to train and host the
card classiﬁcation model on the custom dataset. Since the ESP32-CAM lacks the computational
resources to run neural network inference locally, Roboﬂow’s cloud API acts as the inference
engine of the pipeline. The ESP32-CAM submits each captured frame as a base64-encoded Joint
Photographic Experts Group image format (JPEG) to the Roboﬂow endpoint over HyperText
Transfer Protocol Secure (HTTPS), and the platform responds with the predicted label and its
conﬁdence score, which are then used to drive the robot’s movement, LED matrix expression,
and audio response.

4.2.2
Image Classiﬁcation Model : ResNet18
ResNet18 [34] is a compact convolutional neural network consisting of 18 layers with
residual connections, designed to achieve reliable classiﬁcation performance while remaining
computationally efﬁcient. Its residual connections allow gradients to ﬂow directly through
shortcut paths during backpropagation, enabling stable convergence even on relatively small
datasets. ResNet18 was selected as the classiﬁcation backbone for this sprint because its
balance between accuracy and inference speed makes it well suited to a thirteen-class problem
covering movement control commands, emotional expressions, and safety conditions, within

4.3.5
Sprint Planning
Sprint planning for the auto mode feature involved deﬁning the system architecture and
identifying the technical components required to deliver the full detection pipeline. This section
presents the architectural design that guided the implementation, detailing how the hardware,
ﬁrmware, cloud inference, and web interface layers were structured and connected to achieve
autonomous card-driven robot control.
4.3.5.1
Sprint Architecture
The auto mode sprint is built around a multi-component architecture that connects physical
hardware, embedded ﬁrmware, cloud inference, and a web interface into a single cohesive
pipeline. At the hardware level, a physical switch connected to the ESP32 serves as the entry
Page 87


===== PAGE 106 =====

CHAPITRE 4. SPRINT 3 : VISION-BASED MODE
point of the entire ﬂow, toggling the system between manual and auto mode. When auto
mode is activated, the ESP32 simultaneously notiﬁes the web application through a persistent
WebSocket channel and instructs the ESP32-CAM to begin its detection loop via a local HTTP
POST to the /start endpoint.
The ESP32-CAM operates as an independent node on the same local Wi-Fi network,
capturing frames from its OV2640 sensor and submitting them over an encrypted HTTPS
connection to the Roboﬂow cloud inference API, which runs the trained ResNet18 model and
returns the predicted label and conﬁdence score. The ESP32-CAM then forwards these results
to the ESP32 via a local HTTP POST to the /detected endpoint. The ESP32 in turn executes
the corresponding command — driving the motors, triggering the DFPlayer audio module,
and updating the LED matrix — and broadcasts the label and conﬁdence score to the web
application over WebSocket.
In parallel and independently of the detection pipeline, the web application opens a direct
HTTP connection to the ESP32-CAM’s MJPEG stream endpoint at port 81, receiving and
displaying a continuous live video feed in a full-screen overlay that takes over the interface
for the duration of auto mode.
This architecture clearly separates concerns across its components : the ESP32 handles
coordination and actuation, the ESP32-CAM handles vision and inference communication,
Roboﬂow handles the machine learning computation, and the web application handles
visualization. This separation ensures that each layer remains focused, maintainable, and
independently testable.

Conclusion
This sprint has successfully delivered a fully functional automatic card-recognition and
command-execution system for the educational robot. The integration of a ResNet18 image
classiﬁcation model trained on thirteen card classes, a real-time detection loop, and a structured
WebSocket command pipeline has endowed the robot with the ability to operate autonomously
in response to physical card input. The robot can now recognise movement control cards and
execute the corresponding motor sequences, detect edge and obstacle conditions and react to
them safely using its onboard sensors, and display matching emotional expressions on the LED
matrix without any manual intervention from the student.
This autonomous interaction layer, built upon a well-deﬁned architecture connecting the
React web application, the ESP32-CAM vision module, the Roboﬂow inference API, and the

GENERAL CONCLUSION AND PERSPECTIVES
General Conclusion And Perspectives
Bridging the gap between young learners and the foundational concepts of programming,
robotics, and artiﬁcial intelligence demands more than motivation — it calls for creativity,
accessibility, and a system that children genuinely want to engage with. This project embraced
that mission, resulting in the creation of an interactive educational platform that brings together
a physical robot, a web application, and an AI-driven vision pipeline into a single, coherent
learning experience.
Through three development sprints, a complete hardware foundation was assembled and
validated, a cross-platform web application was built with role-based interfaces for students,
teachers, and administrators, and a vision-based auto mode was introduced that allows the robot
to recognize physical sign cards in real time and respond with movement, audio, and live visual
feedback — making artiﬁcial intelligence tangible for young learners.
Looking ahead, future work will focus on advancing the AI pipeline to support
local on-device inference, expanding the library of learning modules with storytelling and
collaborative challenges, and deploying EduBot in real classroom environments to gather the
feedback needed for meaningful iteration. Ultimately, this project establishes more than a
