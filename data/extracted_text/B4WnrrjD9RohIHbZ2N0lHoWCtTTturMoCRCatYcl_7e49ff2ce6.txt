Beyond financial considerations, vehicle theft generates significant social and psy-
chological impacts. According to a 2021 survey conducted by the Tunisian Consumer
Protection Organization[3], 67% of respondents expressed moderate to high concern
about vehicle theft, with 42% reporting they had adjusted their parking or travel habits
due to theft concerns.

Things (IoT), biometrics, and computer vision, enhance vehicle security with features
such as real-time tracking and driver identification. However, these technologies possess
inherent limitations: computer vision requires optimal conditions, AI algorithms can
produce inaccuracies, IoT devices depend on secure network connectivity, and biometric
systems may face precision challenges. Furthermore, they introduce cybersecurity

In today’s rapidly evolving threat landscape, organizations rely on a variety of ad-

3.1
Zero trust architecture
Traditional perimeter defense proves inadequate as cloud services, mobile work-
forces, and IoT devices erode the secure network perimeter, necessitating a security
paradigm for internal/external threats. Zero Trust Architecture (ZTA) [10] represents
this paradigm shift. Its core principle, Zero Trust, mandates continuous verification,
rejecting implicit trust. This section explores ZTA’s foundations, components, and
implementation strategies, detailing how applying Zero Trust concepts via identity
verification, continuous monitoring, and encryption enhances security, performance,
and usability.
Historical context and evolution
The concept of Zero Trust has been present in cybersecurity discourse for over a decade
[11], though its formal articulation and widespread adoption are more recent devel-
opments. The Defense Information Systems Agency (DISA) and the Department of
Defense pioneered early work on a more secure enterprise strategy called ”black core,”
which involved moving away from perimeter-based security to focus on individual
transactions.
The Zero Trust security model As shown in 3.1, first inspired by the Jericho Forum’s
2004 concept of de-perimeterization and later defined by John Kindervag, shifts trust
from network location to transaction-level validation. It evolved due to remote work,
BYOD, cloud use, advanced cyber threats, and compliance demands. Supported by
federal initiatives like FISMA and CDM, it replaces static defenses with dynamic, fine-
grained access control based on the principle of ”need to access,” reducing risks from
breaches and compromised accounts.

3.1.1
Core principles of zero trust architecture
NIST SP 800-207’s Zero Trust Architecture (ZTA) fundamentally redefines security by
treating all assets as resources, securing all communications regardless of network
origin, and granting access on a strictly per-session basis. ZTA operationalizes this
through dynamic policy enforcement, continuous monitoring of asset security posture,

===== PAGE 34 =====

State-of-the-Art in Security Technologies
ongoing dynamic authentication/authorization [13], and comprehensive data collection
to inform security decisions. These principles serve as an ideal, with organizations
tailoring implementation to their specific context and risk tolerance.
• All assets as resources: Every data source, computing service, IoT device, or personal
device accessing enterprise systems is considered a resource requiring protection.
• Universal secure communication: All communication is secured (e.g., via encryption,
authentication) regardless of network location (internal or external).
• Per-Session access control: Access to resources is granted ephemerally for each
session, requiring independent authentication and authorization.
• Dynamic policy enforcement: Access decisions are based on dynamic policies incor-
porating multiple attributes (e.g., user identity, device status, behavior, environment).
• Continuous asset monitoring: The integrity and security posture of all owned and
associated assets are continuously monitored and measured.
• Dynamic authentication & authorization: Authentication and authorization are
dynamic, strictly enforced, and continuously re-evaluated throughout sessions.
• Data-driven security decisions: Information on assets, network infrastructure, and
communications is actively collected and analyzed to improve security posture and
inform policies.

• Default untrust: All entities (devices, users, services) are untrusted; interactions with

3.2.1
Definition and technical workflow of face recognition :
Face recognition begins with camera input capturing live facial imagery, which is first
processed by a computer vision model to detect and align facial regions [15]. Next, a
deep learning network extracts high-dimensional feature representations from these
aligned face patches [16]. During enrollment, each user’s feature vector is stored in the
system database as a compact embedding [17]. At authentication time, the incoming
frame is passed through the same pipeline to generate a live embedding, which is then
compared against stored embeddings using a similarity metric—commonly Euclidean
or cosine distance—with matches below a set threshold confirming the user’s identity
[18].

3.3
Anti-spoofing
Anti-spoofing technologies are a critical defense in biometric systems against sophisti-
cated presentation attacks [22]. While face recognition offers convenient authentication,
it remains vulnerable without such safeguards. This section reviews anti-spoofing
concepts, challenges, and approaches.
3.3.1
The spoofing vulnerabilities and attacks
Face recognition systems are vulnerable to presentation attacks (PAs), where non-
genuine biometrics are presented to impersonate users. Common face spoofing methods
include:
• Print attacks: High-quality printed user photographs.
• Replay attacks: User videos/images on screens (e.g., smartphones, tablets).
• 3D Mask attacks: Realistic 3D masks/models simulating facial structure.
• Deepfake attacks: AI-generated synthetic media mimicking real faces.
These vulnerabilities pose significant security risks, especially in high-stakes appli-
cations, risking substantial losses or data compromise. The challenge is developing
efficient, robust detection methods for resource-constrained devices against diverse,
evolving spoofing techniques [23].
3.3.2
Anti-spoofing approaches
Contemporary anti-spoofing (Presentation Attack Detection - PAD) methods employ
diverse strategies As illustrated in Figure 3.6:
• Texture analysis: Detects visual artifacts (e.g., print patterns, screen pixels) and
texture patterns differentiating real skin from artificial materials in Presentation
Attacks (PAs).
• Motion detection: Analyzes natural facial/head movements and micro-expressions
(e.g., eye blinks) that are difficult to replicate in static or simple replay PAs.

===== PAGE 41 =====

State-of-the-Art in Security Technologies
• Depth information: Utilizes depth sensors (e.g., Time-of-Flight, structured light)
or stereo vision to verify 3D facial structure, often absent or incorrect in 2D PAs.
• Reflectance analysis: Examines light interaction with the facial surface, as skin
has unique reflective/scattering properties compared to materials like paper or
LCD screens.
• Multi-spectral analysis: Uses multiple light wavelengths (e.g., visible, infrared)
to identify biological markers or material properties unique to living tissue.
• Challenge-response: Prompts the user for a specific action (e.g., smile, turn head)
and verifies the response.

ZTA’s ”never trust, always verify” principle. This ensures the entity is both correctly

3.4
Hybrid encryption
Hybrid encryption combines efficient symmetric encryption with asymmetric (public-
key) encryption’s key management benefits. It leverages both for robust data security,
especially for large data volumes and secure key distribution.
3.4.1
Rationale for hybrid encryption
Data encryption must balance security, performance, and key management. Symmetric
algorithms (e.g., AES) [24] are fast for bulk data but face key distribution challenges.
Asymmetric algorithms (e.g., RSA) [25] solve key distribution via public/private keys
but are too slow for large data.
Hybrid encryption combines fast symmetric encryption for data with secure asym-
metric encryption for the session key, ensuring efficient and strong end-to-end security.
Only the recipient with the private key can decrypt the session key, keeping data safe
even if intercepted.

Technical benefits of Supabase:
• Relational database (PostgreSQL): Supabase leverages the full power of Post-
greSQL, a mature and reliable relational database engine. It efficiently handles
complex data relationships (one-to-many, many-to-one), making it ideal for mod-

• Real-time subscriptions: Using Postgres Realtime, Supabase enables live data

• Cloud-Native scalability: Supabase is designed for horizontal scalability and

• Accelerated development workflow: With support for RESTful APIs, GraphQL,

Product-user relationship
The products table lies at the heart of the system’s hard-
ware integration. Each row in this table corresponds to a physical security module—a
Raspberry Pi and Arduino setup installed in a vehicle. The database design assumes
that every physical product is globally unique and must be securely tied to a single
user at a time. This is enforced via two critical constraints: unique(product key) and
unique(user id). Together, they ensure that no two users can claim ownership of the
same product and that no user can simultaneously own multiple products, maintain-
ing a strict one-to-one mapping. Each product comes with a product key, which is a
text-based unique identifier stored in .env file during provisioning. This key acts as a
hardware fingerprint, allowing the system to identify the vehicle when it connects to
the cloud. This binding ensures that even if someone clones the code or tampers with
the device, without the correct product key associated with their user ID, they will be
denied access to the vehicle’s features. From a security and traceability standpoint, this
relationship is central. By linking the products table to the users table via a foreign
key (user id), and allowing updates and soft deletes through ON UPDATE CASCADE
and ON DELETE SET NULL, the schema supports ownership transfer without data
loss. This means when a user sells their vehicle or reassigns it, the system can preserve
localization, historical data, and logs, without deleting the entire record—ensuring data
continuity for audit and insurance purposes. Moreover, each product can optionally
be tied to an admin id, forming a triangular association between admin, user, and
device. This reflects the real-world situation where an administrator (e.g., a dealer-
ship, fleet manager, or security operator) might provision devices, monitor usage, or
reset configurations. The admin field is nullable and uses SET NULL on deletion,
meaning the system will continue functioning for the user even if the original admin is
removed—highlighting a resilient design approach. This relationship also serves as
the anchor point for several dependent systems:
• The localisations table references product key, allowing GPS tracking to be
directly tied to the physical device rather than the abstract user. This decouples
tracking from user accounts, enabling more flexibility (e.g., tracking a vehicle even
during guest access or temporary admin control).
• In the future, this architecture supports adding multi-user sharing of a vehicle by
relaxing the unique(user id) constraint and creating a join table (user product access),
enabling scenarios like family vehicles or fleet access with tiered permissions.

Messaging and real-time notifications
A standout feature of the backend is its support
for real-time communication. The messages table handles in-app chat between users
and admins. To ensure asynchronous data relay, a trigger named notify admin is con-
figured to call a backend endpoint via HTTP whenever the table is updated—essentially
acting as a webhook mechanism to push messages directly into a Node.js-powered
chat relay. This kind of trigger bridges the database and server logic, keeping users
informed instantly, which is vital for a reactive security application. In parallel, the
notifications table is used to send discrete alerts to users about system events—such as
a failed facial authentication, GPS movement beyond a safe zone, or a settings update.
Each notification is tracked with a read/unread status and timestamp, forming a mini
audit log for the user.
User profiles and preferences
To support a more customizable and intelligent experi-
ence, the system includes a user profiles table, which stores optional details such as
interests, profile images, and encrypted facial biometric references. These can later
be used to drive machine learning personalization or improve UX. Meanwhile, the
user settings table stores JSON-formatted configurations, giving users full control over
notification preferences, trust zones, or multi-user access setups. This separation of
profile and settings into discrete tables is intentional—it simplifies updates, enhances
modularity, and avoids bloating the main users table. Moreover, all tables with user
ownership enforce on delete cascade, ensuring a secure and clean data lifecycle.

Understanding WebSocket and JWT integration
WebSocket is a full-duplex com-
munication protocol that enables real-time, two-way interaction between a client (e.g.,
mobile or web app) and a server over a single, persistent TCP connection. Unlike HTTP,
which follows a strict request-response model, WebSockets allow either party to send
data at any time without waiting for the other side.
The role of JWT in WebSocket communication
To ensure secure and authorized
communication over WebSockets, we integrate JWT (JSON Web Token) authentication
during the initial handshake phase. The process is as follows:

• 1. Initial handshake: The client initiates a WebSocket connection via HTTP,
including the JWT in the headers or query string.
• 2. Authentication: The backend verifies the JWT to authenticate the user and
validate their permissions.
• 3. Connection upgrade: Once verified, the connection is upgraded to a WebSocket.
• 4. Real-Time event flow: Authenticated clients can now emit and receive events
(e.g., location updates, notifications, messages) through designated channels or
rooms.
• 5. Scoped authorization: Clients can join specific rooms (e.g., chat admin room,
gps tracker room) based on their JWT claims (such as user role or ID).

To ensure precision, performance, and privacy in real-

How does WebSocket work?
WebSocket establishes a persistent, bidirectional com-
munication channel between a client and a server. The process involves three key
stages:
1. Initial handshake (upgrade from HTTP)
The WebSocket protocol begins with an HTTP-based handshake initiated by the client
and upgraded to a persistent WebSocket connection. Here’s a breakdown:
• The client initiates the connection by sending an HTTP request with a special
header: The client sends an HTTP request with Upgrade: websocket and Connec-
tion: Upgrade headers. This signals the server to switch the protocol.

Sprint 2: Mobile–cloud integration (ZTA)
• Server Responds with 101 Switching Protocols: If accepted, the server returns a
101 status, completing the handshake As shown in Figure 5.9 and upgrading the
connection to WebSocket.
• The connection then upgrades from HTTP to WebSocket protocol.
Figure 5.9: Handshake
2. Persistent connection
• Once established, the connection remains open (unlike HTTP’s request-response
cycle).
• Both client and server can send messages at any time without re-establishing the
connection.

3. Event-driven communication
WebSocket operates on an event-driven archi-
tecture, where both the client and server react to specific events triggered during the
lifecycle of the connection. This model enables efficient and responsive real-time com-
munication. The core events in a typical WebSocket implementation are:
• onopen: This event is triggered when the WebSocket connection is successfully
established. It indicates that both the client and server have completed the hand-
shake and can begin exchanging messages.
• onmessage: Fired whenever a message is received from the opposite endpoint.
The message payload can contain plain text, JSON-structured data, or binary
data, depending on the application’s needs. It is the primary means for receiving
real-time data.
• onclose: Called when the connection is closed, either voluntarily by one of the
parties or due to an unexpected disconnection. This event can be used to clean up
resources or attempt reconnection logic.
• onerror: Activated when a communication error occurs on the WebSocket channel.
This can include protocol violations, unexpected disconnections, or issues with
message encoding. Handling this event is important for robust error reporting
and fault tolerance.
• emit (custom event emission): While not part of the native WebSocket API, many
frameworks such as Socket.IO introduce an abstraction where clients and servers
can emit and listen for custom-named events. This pattern enhances modularity
and expressiveness in application design. For example, a client may emit a "join"
event with user data, and the server can listen for it to perform specific logic such
as assigning the client to a private room.
This event-based paradigm makes WebSocket communication intuitive and flexible,
allowing developers to build complex real-time features such as messaging systems,
collaborative tools, and live notifications with minimal overhead.
Socket.IO and why it is used
Socket.IO is a JavaScript library built on top of Web-
Socket that simplifies real-time, bidirectional communication between clients and
servers. It enhances WebSocket by providing additional features and fallback mecha-
nisms to ensure reliable communication across different network conditions and browser
capabilities.
• Fallback support: If WebSocket is unavailable (e.g., due to older browsers or net-
work restrictions), Socket.IO automatically falls back to other transport methods
like HTTP long-polling, ensuring compatibility.
88


===== PAGE 89 =====

Sprint 2: Mobile–cloud integration (ZTA)
• Reconnection Handling: Socket.IO includes built-in mechanisms for automatic
reconnection in case of network interruptions, making applications more robust.
• Room and namespace support: Socket.IO allows grouping clients into rooms or
namespaces, enabling targeted message broadcasting to specific groups rather
than all connected clients.
• Simplified API: It provides a higher-level, event-based API that abstracts much of
the complexity of raw WebSocket, making it easier to implement real-time features
like chat applications or live notifications.
• Cross-browser compatibility: Socket.IO handles inconsistencies across browsers
and devices, ensuring a consistent experience.
Socket.IO is used when developers need a robust, easy-to-use solution for real-time
applications that require more than the basic WebSocket protocol. It is particularly
valuable in scenarios where:
• Applications must support a wide range of clients, including those without Web-
Socket support.
• Developers want to minimize boilerplate code for handling connection issues,
such as dropped connections or network latency.
• Features like broadcasting to specific groups or managing multiple types of events
are needed, as Socket.IO’s rooms and namespaces simplify these tasks.
By abstracting WebSocket complexities and adding features like fallback transports
and reconnection logic, Socket.IO As shown in Figure 5.10 enables developers to build

6.4.1
Analysis
A core requirement for Sprint 2 was to establish a secure method for managing user
sessions and controlling access to NiotoShield’s features. This involved understanding
the need for a robust authentication system capable of handling user identity, roles, and
session lifecycles across various client interactions with the backend.
Authentication with JWT
All interactions between clients and the backend are secured using JSON Web Tokens
(JWTs). Each token encapsulates critical identity information such as the user id, the
user’s role (either user or admin), and a token expiration timestamp. These tokens
are essential for verifying user identity and authorizing access to HTTP endpoints
and WebSocket channels, ensuring a consistent and secure session management
mechanism across platforms.
Secure session management for each user
Managing user sessions securely after login was a foundational requirement. Our goals
were to:
• Guarantee a unique and secure session for every user.
• Protect sensitive information (e.g., names, emails, facial images, live location).
• Enforce role-based access (admin vs. standard user).
• Prevent unauthorized access to key functionalities such as chat, notifications, and
user data.
Final Solution: JSON Web Token (JWT)
We ultimately adopted JWT as the ideal method for session management in a mobile-
first architecture:
• Stateless architecture: Perfect for React Native [45]; no server-side session store
needed.
• Tamper-proof tokens: Signed using a secret key, offering built-in security.
• Role and data encoding: Carries user identity, email, and role information.
• Easy integration: Stored securely using SecureStore or AsyncStorage.
• Access control: Middleware in the backend verifies JWTs for protected routes.

EasyShield: early concept and purpose
As biometric authentication, particularly face recognition, becomes increasingly widespread,
its vulnerability to presentation attacks—such as those using printed photos and screen
replays—poses significant security risks. This sprint initiated the early development of
EasyShield, a lightweight yet robust face anti-spoofing system meticulously designed
to protect these authentication mechanisms. The primary technical and functional need
addressed is the detection of spoofing attempts, with the system designed as a binary
classification model based on the YOLOv12n architecture. This choice was driven
by the requirement for eventual edge deployment, where low computational cost is
paramount.
The core idea behind EasyShield is to establish a computationally efficient security
layer that filters out spoofed inputs before they can reach the primary recognition
system. It is engineered to be fast, lightweight, and capable of operating in real-time on
edge devices with limited resources. In essence, EasyShield acts as a biometric firewall,
scrutinizing inputs to pass only genuine, live faces while blocking fraudulent attempts
with high confidence.
Face recognition systems have become one of the most common ways to do bio-
metric authentication, but they are inherently vulnerable to attack. Today, with just a
printed image or a phone screen, someone can easily bypass many systems by creating
an illusion of the real person. This is called a face spoofing attack, and it’s becoming
increasingly dangerous as these techniques become more sophisticated. Most face recog-
nition models were never designed to detect this kind of attack — they only identify
facial patterns without verifying whether that face is real or fake. The following diagram

Model architecture and classification strategy evolution
The initial objective was to develop a model capable of distinguishing between real
inputs (i.e., live facial footage captured directly by a camera) and spoofing attacks (such

• Initial multi-class approach and re-evaluation: An expansion from binary clas-
sification to a five-class problem was briefly considered and attempted. This
multi-class approach, designed to separate each spoofing type (e.g., screen attack,
printed photo), proved challenging for lightweight models like YOLOv8n, leading
to poor performance and instability.
• Reversion to binary classification: In response to the multi-class challenges,
the design reverted to a binary classification approach (”real” vs. ”spoofed”).
This simplification was deemed crucial for model stability and achieving reliable
performance with limited data and computational resources.
• Adoption of YOLOv12n: To further optimize for edge deployment and address
performance issues, the design incorporated experimentation with the YOLOv12n
model, known for its efficiency.

Ethical and practical considerations
Development of EasyShield v2.5 addressed key ethical and practical considerations:
The false positive vs. false negative tradeoff: balancing false positives (FPs: classi-
fying real faces as spoofed) and false negatives (FNs: classifying spoofed faces as real)
was critical for biometric access due to their asymmetric impact:
• False positives: User frustration, potential legitimate access denial.
• False negatives: System security compromise, unauthorized access.
Development prioritized minimizing FNs, accepting potentially higher FPs, as tempo-
rary inconvenience is preferable to security breaches.
Security-first design philosophy: This philosophy included:
1. Fail-safe approach: Defaults to rejection on high uncertainty.
2. Defense-in-depth: EasyShield as one layer in multi-layered security.
3. Continuous improvement: Modular design for updates against new attack vec-
tors.
Biometric data privacy considerations: To protect privacy:
1. Dataset construction: Training data from public YouTube (implied consent) or
consenting volunteers.
2. Data minimization: Only essential facial regions captured.

9.4.2
Design
The planned solution for achieving automatic cellular connectivity involved several key
design choices:
1. Hardware interface: The SIM7600G-H modem would be connected to the Rasp-
berry Pi via a standard USB interface. This provides both data communication and
power (though external power for the modem might be considered for stability in
some modules).
2. Modem management: ModemManager was chosen as the primary tool for in-
teracting with the SIM7600G-H modem. It handles modem detection, querying
status, and initiating connections, abstracting many low-level AT command com-
plexities.
3. Network interface configuration: The qmi wwan kernel driver, which is suitable for
Qualcomm-based modems like the SIM7600 series, would be used. The associated
network interface (typically wwan0) would be configured to operate in raw ip
mode. This mode allows the IP packets to be passed directly without additional
framing, simplifying the setup.
4. IP Address Acquisition: The udhcpc (a lightweight DHCP client) would be used
to request and obtain an IP address, subnet mask, gateway, and DNS server
information from the cellular network provider over the wwan0 interface once the
modem establishes a data session.
5. Automation: A custom systemd service (sim7600-connect.service) was de-
signed to orchestrate the entire connection process at boot This sequence is shown
simplified in the figure 9.1. The service would:
• Execute after ModemManager.service is active and the network is targeted.
• Include a delay (ExecStartPre=/bin/sleep 30) to allow the modem to ini-
tialize fully after power-on.
• Use mmcli to establish the cellular connection with the specified APN.
• Ensure the qmi wwan module is loaded.
• Configure the wwan0 interface: set it down, enable raw ip mode, and bring it
up.
• Invoke udhcpc to obtain an IP address and network configuration for wwan0.
• Add a default route via wwan0 if not set by DHCP.
• Explicitly set DNS servers as a fallback.

access and user data through strong identity management using face recognition with
anti-spoofing measures. Performance optimization requires careful balance between
security and speed, particularly in EasyShield processing and encryption overhead.

continuous monitoring capabilities with updatable AI models, maintaining security
rigor while preserving usability, and implementing Agile sprints to manage system
complexity effectively.
Insights
The project reinforced the importance of enforcing a Zero Trust security culture while
maintaining optimal UX-security balance through fast, secure face recognition and clear
user alerts. System reliability requires stable power management, adequate compute
resources, and robust connectivity solutions. Phased Agile methodology proved crucial
for successful integration across multiple complex subsystems.
