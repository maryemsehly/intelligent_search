General Introduction
In the context of software system development, Unified Modeling Language (UML) plays a fun-
damental role as a standard visual modeling language. It allows for a structured representation of
functional requirements, business processes, and the software architecture of a project. This repre-
sentation facilitates communication between various stakeholders (analysts, developers, and project
managers) and ensures a better understanding of the system to be designed.
Visual modeling, through standardized diagrams, such as use cases, class diagrams, and sequence
diagrams, is an essential step in ensuring the coherence, maintainability, and scalability of applica-
tions. It serves as a bridge between the expression of requirements in natural language and their
technical implementation, while reducing ambiguities and the risk of errors from the earliest phases
of the software development lifecycle.
Recent progress in Natural Language Processing (NLP), especially with Large Language Model
(LLM) techniques, has introduced innovative methods to assist UML designers during the require-
ment analysis and modeling stages. By applying NLP with LLM techniques, it becomes possible
to automatically identify and generate UML elements directly from textual descriptions. This syn-
ergy enables the creation of intelligent modeling tools capable of transforming natural language into
structured and accurate visual representations.
This project follows this trend by presenting a UML Support Tool based on NLP techniques, with
the goal of facilitating the generation of visual models from textual descriptions.
To achieve this objective, the report is structured as follows:

solution, and adopted methodology.

nical strategy, including UML modeling approach and technology selection.

effective processing.

2.2.1
UML Diagrams Selection
Based on an extensive review of industry practices, including the article: Which UML Diagrams are
Mostly Used? [5], the following three UML diagrams have been identified as the most effective for
system modeling. These diagrams were selected because of their ability to accurately represent both
the static and dynamic aspects of a system, as well as to capture essential functional requirements.
Class Diagram:
A Class Diagram is a static diagram that illustrates the structure of a system by
showing its classes, attributes, methods, and the relationships among them, including associations,
generalizations, and dependencies. It is used to model the system’s architecture, provide a blueprint
for implementation, and ensure that developers and stakeholders understand the organization and
interaction of the system’s components. Class diagrams are particularly useful during the design
phase for defining object-oriented structures and validating the logical architecture of the system.
Use Case Diagram:
A Use Case Diagram is a behavioral diagram that represents the interactions
between external actors (such as users or other systems) and the system itself. It is used to capture and
illustrate the functional requirements of a system, define its boundaries, and communicate how the
system is intended to be used. Use Case diagrams help ensure alignment between stakeholders and
technical teams by providing a high-level view of system functionality and identifying all possible
user interactions with the system.
Sequence Diagram:
A Sequence Diagram is a dynamic diagram that shows how objects interact
in a particular scenario over time, emphasizing the chronological order of messages exchanged be-
tween them. It is used to model the flow of operations, illustrate system behavior, and document
interactions for specific use cases. Sequence diagrams are particularly valuable for understanding and
verifying the temporal aspects of system processes, such as workflows, data exchanges, and method
calls between components.

Technological Foundations of Existing Tools
The technology stack behind UML generation tools is composed of several key components, each
playing a crucial role in ensuring efficiency, scalability, and seamless integration. These components
include.
Rule-Based Reasoning (Ontologies):
A symbolic method that encodes domain knowledge, rules,
and relationships in a formalized structure. Ontologies provide explicit guidance for interpreting the
elements extracted from text and for validating the generated UML diagrams. This reasoning layer
ensures logical consistency, adherence to modeling standards, and supports the integration of domain-
specific constraints.
Large Language Models (LLMs):
LLMs are advanced models trained on vast collections of text
and programming code. They combine strong language understanding with generative capabilities,
allowing them to interpret complex and nuanced inputs. In the context of UML generation, these
models can examine textual requirements to extract essential components such as actors, classes,
attributes, relationships, and interactions. They can resolve ambiguities, determine the most suitable
types of UML diagrams, and produce precise textual or code-based representations that serve as the
foundation for constructing accurate diagrams. Their performance can be enhanced through targeted
techniques, including:
• Prompt Engineering [8]: A prompt is a carefully instruction given to a language model to
guide its behavior. In UML generation, it helps the model understand exactly what elements to
extract and how to represent them clearly.
• Fine-Tuning [9]: Fine-tuning is the process of further training an existing language model
on specific examples to improve its performance in a particular task. For UML generation,
this allows the model to better recognize domain-specific terms and relationships, producing
diagrams that are more accurate and consistent.
Diagram-as-Code Generators:
Diagram-as-Code generators are specialized software components
that convert structured textual representations into visual diagrams. Once the textual input has been
processed and translated into a formalized description, these tools render the graphical UML diagrams
based on that description. Popular frameworks include:
• Mermaid.js [10]: A JavaScript library that enables the generation of flowcharts, sequence
diagrams, class diagrams, and other visualizations directly from simple Markdown-like syntax.
Its integration capabilities make it suitable for embedding diagrams within documentation or
web pages.Figure 2.3 displays the Mermaid logo.

Proposed method
The proposed method emphasizes the integration of Large Language Models (LLMs) with Diagram-
as-Code generation tools. After evaluating several options, PlantUML was chosen as the diagram ren-
dering engine due to its flexibility, ease of use, and support for a wide range of UML diagrams. This
approach automates the creation of UML diagrams from unstructured textual requirements, bridging
the gap between informal stakeholder descriptions and formalized UML models, and enabling a more
efficient and accurate software modeling process.
LLMs, with fine-tuning, analyze the content and context of textual descriptions to identify key ele-
ments such as actors, classes, attributes, relationships, and actions. They organize these elements into
structured representations that can be directly translated into UML syntax, preserving the meaning
and intent of the original requirements while minimizing manual interpretation. Fine-tuning allows
the models to better understand domain-specific terminology and project conventions, improving the
relevance and quality of the extracted elements.
PlantUML then transforms these structured representations into standardized UML diagrams, in-
cluding class diagrams, sequence diagrams, and use case diagrams, ensuring that the generated visuals
are coherent, consistent, and ready for documentation.
Overall, this method combines advanced AI-driven text understanding, with LLMs fine-tuned,
and robust diagram rendering technology, improving modeling accuracy, reducing manual effort, and
facilitating clearer documentation and communication of requirements. It also aligns with CRISP-
DM principles by translating business understanding into actionable, formalized models that guide
subsequent development stages.

Techniques Used for Annotation
Since we already have the PlantUML code as a reliable reference, we used it to guide the annotation
of the natural language descriptions. The code provides a normalized structure, while the descriptions
are expressed in free natural language. To bridge this gap, we applied the following techniques.
1. Regular Expressions (RegEx)
Regular expressions play a crucial role in extracting named entities, whether they are simple
names(one word) or compound names composed of up to three or four words. They are partic-
ularly effective for identifying actors or entities appearing in different text formats, those found
in source code and in textual descriptions.

More specifically, RegEx serves as a bridge between these two formats by addressing variations
are:
• Uppercase and lowercase variations of the same word, which are standardized to ensure
consistent matching.
• CamelCase identifiers in the code, where words are concatenated and capitalized.
• Normal spaced words in textual descriptions, where words are explicitly separated by
spaces.
• Singular and plural forms of the same entity, which are recognized and treated as equiva-
lent references.
By handling these variations, the use of regular expressions significantly improves the accuracy
and consistency of entity name extraction, and this method successfully retrieves about 93% of
the targeted entities.
2. SequenceMatcher
• Definition: SequenceMatcher [14] is a Python tool (from the difflib module) used to
compare two sequences of text and measure their similarity. It returns a similarity ratio
between 0 and 1, where 1 indicates an exact match and 0 indicates no similarity.
• Role: In this method, SequenceMatcher is used to align sentences from the code with nat-
ural language descriptions. Since descriptions can be longer, paraphrased, or formatted
differently, exact matches often fail. This allows detection of textual segments in descrip-
tions that correspond to code components.
• Similarity ratio: A similarity ratio of 0.7 or higher is considered valid.

Modeling Steps
We divide our process into two steps. This allows each model to focus on a single task instead of

model to produce correct, consistent, and executable PlantUML code. This process translates

tegrity, and diagram logic. Special attention is given to the correct use of PlantUML keywords,
syntax symbols, and proper formatting. This ensures that the generated code is directly exe-
cutable and produces accurate UML diagrams.

Separate Models Strategy Implementation
In this phase, we present the implementation of the steps of this strategy, showing how the training of

1. Classification Model
In this model, we selected and evaluated two deep learning architectures, a Bidirectional LSTM (BiL-
STM) and a Bidirectional Recurrent Neural Network (BiRNN), to classify UML diagram types from
their textual descriptions. The main objective is to automatically differentiate between the different
types of diagrams. Both architectures are well suited for sequence-based natural language processing
tasks and were trained on the same dataset to enable a fair and consistent performance comparison.
Bidirectional Long Short-Term Memory (BiLSTM) [19]: Bidirectional LSTM (BiLSTM) is an
extension of the traditional LSTM that processes sequences in both forward and backward directions,
capturing context from the entire text. This is especially useful for UML diagram type classification,
as important cues in the descriptions may appear anywhere in the sequence. By considering both past
and future context, the BiLSTM can more accurately distinguish between the different types.
Bidirectional Recurrent Neural Network (BiRNN) [20]: Bidirectional Recurrent Neural Net-
work (BiRNN) is an extension of the standard RNN that processes sequences in both forward and
backward directions, capturing information from the entire sequence. This bidirectional context is
especially useful for UML diagram type classification, as key cues can appear anywhere in the textual
description. By considering both past and future tokens, the BiRNN can more accurately distinguish
between different types .
Data Preparation
• Loading and Processing Data: Each description was loaded together with its corresponding
label indicating its type.
• Label Encoding: Diagram types were converted into numerical labels required for supervised
classification.
• Data Splitting: The dataset was separated into training and testing subsets to allow objective
performance evaluation, using an 80% training and 20% testing split.
• Tokenization and Padding: Textual descriptions were transformed into numerical sequences
and padded to a fixed length to ensure consistent input dimensions for both BiLSTM and Bidi-
rectional RNN models.
• Additional Considerations: Preprocessing included text normalization, vocabulary size con-
trol, and the use of word embeddings to improve model performance and reduce complexity.

Analysis of the strategies showed that the single model strategy is simpler but less effective with
complex inputs, where errors and inconsistencies in diagram recognition are more frequent. The sep-
arate models strategy provides a structured step: first classify the diagram, then use the corresponding
specialized model for extraction. This method improves accuracy, handles errors better, and maintains
UML consistency for long or complex descriptions.
Regarding the models, Gemma-it was consistently more robust than Flan-T5 across all diagram
types. It accurately extracts elements, tolerates input errors, and preserves structure for extended
descriptions. Flan-T5 performs adequately for simple cases but struggles with complex or lengthy
diagrams.
Based on this evaluation, the separate models strategy and Gemma-it extraction models was se-
lected. This combination ensures accurate, reliable UML extraction and establishes a solid foundation
for the subsequent stages of generation, testing, and system integration.

7.3.3
Model Development and Integration
This section presents the internal workflow of the deployed models, focusing on how each fine-tuned
neural network processes the input text, performs its specialized function, and exchanges data be-
tween components. The complete processing pipeline consists of three core models: the BiLSTM
Classification Model, the Gemma Extraction Model, and the StartCoder2 Code Generation Model.
Classification Model
a. Input Preprocessing and Tokenization
User-provided text is normalized through punctuation removal, lowercasing, and stop-word filter-
ing. A custom tokenizer converts each token into integer indices based on a predefined vocabulary.
Sequences are padded or truncated to a uniform length before being passed into the model.
b. Embedding and Sequence Encoding
Each token index is mapped into a dense embedding vector via a trainable embedding layer. The
sequence is processed by a bidirectional LSTM, which encodes context from both forward and
backward directions. The resulting hidden states are concatenated to form a unified representation
capturing semantic dependencies across the input.
c. Classification Head and Output
The encoded representation is passed through a fully connected layer followed by a softmax ac-
tivation. The output consists of three probability values representing the likelihood of each UML
diagram type: Class, Use Case, or Sequence. The predicted class is then transmitted to the next
model in the pipeline.
Extraction Model
a. Tokenization and Encoding
The model receives both the user input and the predicted diagram type as a structured prompt. This
prompt is tokenized using a SentencePiece tokenizer, which segments the text into subword units
suitable for model processing. Each token is embedded through the Gemma embedding layer and
forwarded to the transformer stack.
b. Transformer Inference Process
The embeddings pass through multiple layers of multi-head self-attention and feed-forward net-
works, supported by residual connections and layer normalization. The attention mechanism cap-
tures contextual relationships, allowing the model to extract key UML components and their de-
pendencies.
c. Output Decoding and Structuring

95


===== PAGE 109 =====

At inference, the decoder generates structured text that represents the UML elements and relation-
ships. This structured output serves as the input for the code generation model.
Code Generation Model
a. Input Formatting and Tokenization
The structured representation produced by the Gemma model is reformatted into a descriptive
textual prompt designed to guide PlantUML generation. The prompt is tokenized using the Star-
Coder2 tokenizer, which converts textual tokens into numerical identifiers.
b. Autoregressive Generation
Each token embedding is passed through multiple self-attention layers, enabling the model to learn
structural and syntactic dependencies. The decoder generates PlantUML code token by token in
an autoregressive manner, conditioned on the previously generated context.
c. Output Formatting
The output is formatted with standard PlantUML delimiters (@startuml and @enduml) and vali-
dated for syntax correctness. The final PlantUML code is sent back to the local frontend via Ngrok,
enabling rendering and exporting.

General Conclusion
This project aimed to design, develop, and deploy an automated UML diagram generation system,
called D-UML, based on LLMs techniques . The main objective was to bridge the gap between textual
requirement specifications and formal software design by enabling the automatic transformation of
natural language descriptions into UML diagrams. The project focused on creating a system capable
of supporting multiple diagram types, including Use Case, Class, and Sequence diagrams, in both
French and English, providing multilingual support for a diverse range of users and use cases.
A critical step in this project was the preparation of a robust bilingual dataset by combining two
different sources: textual descriptions in French and English and corresponding PlantUML code ex-
amples. Through rigorous data cleaning, standardization, translation, and annotation, these sources

Abstract
This project presents a bilingual solution (French and English) leveraging Large Language Models
(LLMs) for automatic UML diagram generation and visual modeling from natural language descrip-
tions. The D-UML application integrates three main modules: a BiLSTM classification model that
identifies the UML diagram type (Use Case, Class, Sequence), fine-tuned GEMMA IT extraction
models that analyze and structure the textual input, and a StartCoder generation module that converts
the structured output into executable PlantUML code to produce a visual UML diagram. This end-to-
end pipeline automates the interpretation, structuring, and visual representation of software scenarios,
simplifying the modeling process and reducing manual design effort.
Keywords: UML, Visual modeling, Automatic UML diagram generation, Class diagram, Use
Case diagram, Sequence diagram, LLMs, NLP, GEMMA-IT, StartCoder, Fine-tuning
