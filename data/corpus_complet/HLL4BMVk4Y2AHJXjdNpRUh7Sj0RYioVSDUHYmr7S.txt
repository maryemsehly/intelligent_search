General Introduction
Gamefy Academy is a gaming centre in La Soukra, in the northern suburbs of Tunis.
Players rent time on its gaming terminals, buy drinks and snacks at the counter, and
the regulars belong to a loyalty programme. From the day the centre opened, the point
of sale software recorded all of it: every session played, every cash payment and every
item sold. By the time I arrived for my internship, almost a year of that history had
piled up in Excel files on a local drive, and not a single tool was reading any of it.
The owner ran the centre on instinct and daily experience, setting prices, staffing
and stock without looking at the numbers. The data existed, but it played no part in
the decisions.
The project set out to close that gap. The deliverable is a web application that
the owner opens in a browser. Behind it sit an ETL pipeline that reads the raw Excel
exports, a star schema that holds the clean data, the forecasting and segmentation
modules, and an embedded chatbot. Power BI was used early on, only to prototype the
dashboards and confirm the KPI definitions with the owner.
The source data proved messier than it first appeared. The files opened correctly in
Excel, but reading them in Python surfaced encoding errors, unusual number formats,
and columns shifted by merged cells. None of this was documented anywhere, and
resolving it took a large part of the work.
The project was managed with a hybrid approach that combines two methods.
GIMSI, a Business Intelligence method, guided the data and dashboard design: it starts
from the owner’s goals and the KPIs before any chart is built. Scrum organised the
build itself, since a data project rarely shows its real shape until the files are opened,
and the room to adapt between sprints matters more than a fixed plan. The work was
split into four sprints, one for preparation and three that each end with a working piece
the owner can use.
The report follows these sprints. Chapter 1 presents the host centre, the existing
system and the solution I propose. Chapter 2 is Sprint 1, the preparation and the
data warehouse: the requirements, the backlog, the schedule, the architecture, the
dimensional model, the ETL pipeline that builds the star schema, and a short note
about Power BI. Chapter 3 is Sprint 2, which delivers the login screen and the session
system. Chapter 4 is Sprint 3, which delivers the backend, the three dashboards, the
upload page and the settings page. Chapter 5 is Sprint 4, which delivers the forecasts,
the member segmentation, the anomaly alerts and the chatbot. A general conclusion
closes the report.

1.3.4
Problem Statement
Gamefy collects detailed operational data every day. It gets almost no value from it.
The question this project tries to answer is:
How can these raw Excel exports, full of formatting issues, be turned into
a clean, reliable dataset that the owner can actually use to look at the past
and plan for the next months?
The word reliable matters. A one-time manual clean is not a solution. The centre
needs a process that can be re-run whenever the files change.
1.3.5
Proposed Solution
The proposed solution is GamefyDB. It is built in five layers and runs from a single
command.
1. An ETL pipeline reads the four source files, strips every formatting artefact,
corrects missing cashier names, types the columns correctly and builds a six-table
star schema.
2. A forecasting module compares four time-series models: Prophet, SARIMA,
Holt-Winters and XGBoost. Two of them accept a weather regressor from the
Open-Meteo API.
3. A segmentation module groups members into four behavioural profiles using
K-Means and produces a continuous loyalty score per member.
4. An anomaly detector flags days where revenue, session volume or member activity
was unusual relative to the same day of the week.
5. A web application brings everything together: a login screen, dashboards, forecasts,
an upload page, a settings page and an embedded chatbot. The web application
is the final product.
A Power BI report was built early in the project to prototype the dashboard layout
and to agree on the KPI definitions with the owner. Chapter 2 explains how it fed into
the web application.
The real data came in two batches. The first export covered six months. A second
export added the rest, bringing the real window to about eleven months (June 2025 to
April 2026). Even that is not enough for a seasonal model to learn a full yearly pattern,
so a synthetic generator was used on top to extend the history further. It samples from
the real daily revenue pool and applies Ramadan, Eid, monthly and weather multipliers.
Without this step the time-series models would not have enough history to learn a
yearly cycle.

2.5
Technical Architecture
The global design follows the data itself. It travels from the point of sale exports,
through the pipeline, and into the dashboards and the forecasts.
2.5.1
Layered Design
The design is flat on purpose. The source layer is the four Excel files in the input
folder, plus a cached weather file and a set of synthetic extended files used to give
the time-series models enough history. The processing layer is a small set of Python
modules: one for the ETL, one for the forecasters, one for the segmenter and one for
the anomaly detector. The output layer is two folders. One holds the star schema. The
other holds the analytics outputs. The web application and the chatbot both read from
those folders.
The ETL is kept in one file instead of being split into four files for read, clean,
transform and export. This was on purpose. The cleaning depends on how each source
file is built. Putting it into a generic cleaner would add more code without making it
clearer.

The stack has three parts. A Python layer does the data work: the ETL, the forecasting,
the segmentation and the anomaly detection. A FastAPI backend loads the star schema
into DuckDB and serves it as JSON. A React single-page application calls the backend
and draws the dashboards, with a Streamlit chatbot embedded inside it. In production
the three parts run behind a single domain: the backend serves the built React files, the

2.6.3
Design Approaches
Inmon Approach
Bill Inmon’s approach is top-down [3]. You begin by building one big, fully normalised
warehouse for the whole company, then carve smaller data marts out of it, one per
subject. Normalisation stops the same data from being stored twice. The catch is real,
though: you have to design the entire warehouse before a single report can come out of
it. Figure 2.3 shows the shape of this approach.
Figure 2.3: The Inmon data warehouse approach.
Kimball Approach
Ralph Kimball’s approach goes the other way, bottom-up [2]. Each business process is
modelled as its own star schema first, and the marts are stitched together later through
shared dimensions. The payoff is speed: usable output reaches the analysts much sooner.
Figure 2.4 shows the shape of this approach.

GamefyDB

Figure 2.4: The Kimball data warehouse approach.
Adopted Approach
I went with Kimball. With only four business areas, one location and a short timeline,
building a full normalised warehouse first would have eaten the whole internship before
a single dashboard appeared. Bottom-up let me check each output table against the
real data as I built it, and fix things before moving on. The shared cashier and terminal
dimensions give the links between areas that Kimball asks for.

Multidimensional Modelling
Three modelling patterns are worth weighing here, and one of them, the galaxy schema,
fits GamefyDB best. The next paragraphs say why.
2.7.1
Conceptual Model Analysis
A conceptual model gives a high-level view of the data and how its parts connect, before
any real table is built. Three patterns are common in data warehousing, and I looked
at each one against the GamefyDB data.
• Star schema. One central fact table surrounded by dimension tables that are
not split any further. It is simple to read and fast to query, and Power BI works
well on top of it. Its limit is that it covers one business process at a time.
• Snowflake schema. An extension of the star, where each dimension is broken
into several linked tables. This lowers redundancy and keeps the data tidy, but it
adds joins and makes the queries heavier.

• Galaxy schema, also called a fact constellation. Several fact tables that share
the same dimensions. It can describe more than one business process at once,
which is what a centre with both sales and gaming sessions needs.

2.7.2
Choice of Conceptual Model
Of the three, the galaxy schema fits GamefyDB best. A star schema would push the two
activities, cash transactions and gaming sessions, into one fact table or into two separate
stars that no longer share their common dimensions. A snowflake would normalise
dimensions that do not need it, since they are small and rarely change, and it would
only add joins to every query. The galaxy keeps one shared set of dimensions and gives
each activity its own fact table.
Two fact tables (fact_transaction and fact_session) share three dimensions (dim_cashier,
dim_terminal, dim_member). The item dimension is used only by the transaction fact.
Stock movements and the per-member totals were folded into the item and member
dimensions during the build. The reason is simple: stock only moves in one direction
(out, when sold), and the members file gives a running total per member instead of
one row per event. Adding fact tables for them would not have brought any new
information.

Reading the files.
All four files are read without a declared header. The whole sheet
is loaded as a raw table with numbered columns. Automatic header detection cannot
be used because merged cells move the data to different columns than expected. For
example, in the cash file the title of the category column is at one index, but the actual
category values sit at a different one. The only way to know the right position is to
look at real rows. The map of column indices is built once per file from this check. This
is the most fragile part of the pipeline. If the point of sale software ever changes the
export format, these indices have to be checked again.
Handling the members file.
The members file will not open with the default
Python Excel reader on Windows. It throws a charmap encoding error before the first
row is read. The fix uses a lower-level Excel reader that opens the sheet without trying
to convert the characters. The cleaning then runs row by row.
Removing page-break artefacts.
The export software adds a page-break group
every 40 rows or so: a Page X/Y label, two empty rows and a full copy of the headers.
A header-row check runs on every row first. It tests three things: the value is empty,
the value equals the word Cashier (the first column header in every file), or the value
looks like the date pattern used in the page-marker rows. Any row that matches on its
main column is dropped.

Parsing TND amounts.
The TND amount format is the most unusual issue. A
value like 1 745,44 TND looks normal in Excel. The space between 1 and 745 is a narrow
no-break space (Unicode U+202F), not a regular space. Standard parsers reject it. This
issue took about half a day to identify. Plain str.strip() left the strings the same
length, and I found the cause only after pasting a value into a Unicode inspector and
seeing the U+202F codepoint. After that the fix was easy: the parser removes every
kind of space, drops the TND suffix, replaces the comma with a period, and turns the
result into a number. If the conversion still fails, the value is marked as missing and
handled later.

Session Management
The session uses a cookie marked HttpOnly, Secure, and SameSite. HttpOnly means a
script in the browser cannot read the cookie, which stops a common way of stealing a
session. The cookie was chosen over a token in local storage because the web app and
the API share the same domain in production.
Each account carries a role, either admin or cashier. The admin account is the
owner. A cashier account is limited to the pages the owner turns on. The frontend
hides the menu items a user is not allowed to see, and the backend still runs the same
check on every request.
3.5.5
Security and Limitations
A few security choices are worth stating plainly, along with what was left out. Passwords
are stored only as hashes, never in plain text. The session cookie is marked SameSite,
which blocks the basic cross-site request forgery case where another site tries to post to
the API on the user’s behalf. User input never reaches a raw SQL string: the endpoints
run fixed queries over the star schema, and the chatbot can only call a fixed set of tools
rather than write its own SQL, so there is no place to inject a query.
What is missing is just as important for an honest account. There is no rate limiting
on the login endpoint, so nothing yet slows down a script that tries many passwords in
a row. The app is also meant for one small trusted team on a local network, not for the
open internet. Adding login rate limiting and a lockout after repeated failures is the
first hardening step before any wider deployment.

5.5.2
Time Series Fundamentals
Forecasting needs an understanding of trend, seasonality and noise. This section covers
the time series basics, the stationarity check, the data preparation and the train-test
split used for every model.
Time Series Concepts
A time series is a list of values measured at fixed time steps. It is usually split into
three parts.
• Trend (Tt). The general direction of the series over a long period.
• Seasonal pattern (St). The regular ups and downs that come back at the same
time each year, month or week.
• Leftover (ϵt). The random part that the trend and the seasonal pattern do not
explain.
Stationarity Study
Before fitting a model, the series should be checked for stationarity. A series is stationary
when its mean and variance stay the same over time. Most classical models need a
stationary series to give reliable forecasts.
Graphical method.
The series is plotted with a centred rolling mean, and checked
for drift or seasonal swings.
65


===== PAGE 67 =====

GamefyDB
CHAPTER 5. SPRINT 4: FORECASTS, ANALYTICS AND CHATBOT
ADF test.
The Augmented Dickey-Fuller test gives a yes/no answer based on a
p-value. It uses two hypotheses.
• H0: the series has a unit root. It is non-stationary.
• H1: the series has no unit root. It is stationary.
If the p-value is below 0.05, H0 is rejected and the series is treated as stationary.
The test was run on the two monthly series used for forecasting: revenue and session
count. The adfuller call returned p-values well above 0.05 on both the raw and
log-transformed series, so the series are treated as non-stationary.
Stabilization.
When a series fails the test, a stabilization step is applied. The
transform is the log of (1 + yt) followed by a first difference:
˜yt = log(1 + yt),
∆˜yt = ˜yt −˜yt−1.
The log step shrinks the variance. The first difference removes any leftover trend.
This transform is used only for the Holt-Winters input. SARIMA already differences
the series through its d and D orders, Prophet handles the trend on its own, and
XGBoost does not need a stationary input. Applying the transform to all four would
mean differencing the series twice for SARIMA, which is not wanted.
Exploratory Analysis and Data Preparation
The star schema has one row per transaction or per session. Forecasting needs one
value per time step. Three preparation steps were applied.
Daily and monthly grouping.
For revenue and session forecasting, the transaction
tables are grouped by calendar day and summed. The daily series is then grouped into
months for the long-range comparison.
Scaling for segmentation.
K-Means uses distances between points, so features with
larger numbers take over the distance computation. The three behavioural features
were scaled to the same range before fitting.
Extending the history.
The real data came in two parts: six months at first, then
a second batch that brought the real window to about eleven months (June 2025 to
April 2026). That is still under one full year, so a generator extends the history by
sampling from the real daily revenue values and applying Ramadan, Eid, monthly and
weather multipliers, since eleven months is not enough for the seasonal models to pick
up a yearly cycle. Running the model comparison on this extended history is still worth
doing. It is not proof that one model beats another on the real centre. What it does
is exercise the whole forecasting pipeline end to end and leave behind tested, working
code that will run on the real series unchanged once a second year of data is available.

Evaluation Metrics
Three measures are used together, each reading the error in a different way. The first
two stay in the unit of the data, while the third puts it on a percentage scale.
• MAE (Mean Absolute Error): the average of the absolute differences between
the predicted and the real values. Given in the same unit as the data.
• RMSE (Root Mean Squared Error): the square root of the average of the squared
errors. A single very bad prediction has a bigger effect on the score.
• wMAPE (Weighted Mean Absolute Percentage Error): the total absolute error
divided by the total of the real values, given as a percentage. It puts the MAE on
a percentage scale, so a score can be read across series with different sizes. The
plain MAPE was avoided on purpose, because the centre has many near-zero days
and dividing by a tiny value makes the plain MAPE explode. As a rough guide, a
wMAPE under 20% is treated as good and under 50% as usable.
Threats to Validity
These scores come with a real limit that shapes what they mean. Because the history
is mostly synthetic, the comparison really measures how well each algorithm recovers a
pattern it was already given. How much money actually comes in next year is another
matter, and answering it would take a second year of real data. Once that data exists,
the same code would give forecasts the owner could act on.
The real data window is about eleven months, built in two parts. A seasonal model
needs at least twelve months to learn a yearly pattern, so even the full real window
is short. To run the comparison at all, the monthly series were extended with the
synthetic generator, so the yearly pattern the models learn is, in large part, the pattern
the generator puts in. The XGBoost result on sessions sits in the same trap: one of its
strongest features is the value at the same point in the previous year, and with under
a year of real data that lag is mostly synthetic. The test window also overlaps with
Ramadan, when the centre runs on a different schedule. The numbers below let me
compare the methods against each other on the same data. They say very little about
how far off next year’s revenue would really be.
One more limit is in the method, not the data. Each model is scored on a single
70/30 split rather than on rolling-origin cross-validation, where the split is moved
forward step by step and the model is re-scored at each position. Rolling-origin would
give a steadier estimate, but with so few months it would leave almost no training data
in the early folds, so a single time-ordered split was the more honest choice here. With
a second year of data, moving to rolling-origin folds is the natural next step.

Member Segmentation
Rather than treating all customers the same, we group them by behaviour: Heavy
Users, Casual Spenders, Regulars and Light Users. This segmentation guides how the
owner treats each group.

Objective
The goal is to put members into groups based on how they behave, so the owner can
treat each group differently.
Feature Selection
Two features were used: total spend and total session time. Two other features were
dropped after looking at the data, because they were zero for almost every member:
USB top-up (zero for everyone) and snack bar spend (a value for only two of the 66
members). Keeping them only added noise and pulled the clusters apart in a way that
did not reflect real behaviour. Spend and session time are both heavily skewed, with
a few members far above the rest, so each feature was log-scaled before fitting. That
stops a handful of big spenders from deciding the whole split on their own.
The segmentation has a clear scope limit. The point of sale exports do not give a
reliable per-member visit history, so I could not compute a recency feature (days since
last visit). Total spend is monetary and total session time is engagement. There is no
recency signal here, so I stopped short of calling it RFM. It groups members by spend
and engagement, the part of the data I actually trust.
Choice of k
The elbow method was used to choose the number of clusters. The plot shows the inertia
inside the clusters against k, and the bend in the curve is at k = 4 (Figure 5.16). With
the log-scaled features the four groups come out at a sensible spread: 6 Heavy Users,
18 Regulars, 30 Casual Spenders and 12 Light Users (Figure 5.17). Most members sit
in the middle tiers, which matches what the owner expects.
The silhouette score was also computed to check how well the clusters separate. It
came out around 0.59, which is acceptable for a dataset this small: the four tiers are
distinct enough to be useful without claiming perfectly sharp boundaries. The owner
confirmed that the Heavy Users and Regulars groups match what he sees day to day.
With only 66 members the segment sizes should still be read as a guide, not as exact

Continuous Loyalty Score
Next to the four segments, the segmenter also gives each member a loyalty label. Two
scores are computed using quartiles: one on total spend (m score) and one on total
session time (f score). One naming note matters here. In the classic RFM model the f
stands for frequency, the number of visits. The source data gives no reliable per-visit
count for members, so the f score here measures total session time instead, and the
recency part of RFM is dropped entirely. The score is therefore an FM score, spend and
engagement only, not an RFM score. Adding the two parts gives an FM score between
2 and 8, which is turned into four tiers: Bronze (2 or 3), Silver (4 or 5), Gold (6 or 7)
and Platinum (8). These tiers are shown on the Members page, with a filter to look at
one tier at a time. The chatbot uses the same tiers when the owner asks for the best
customers.
5.5.6
Anomaly Detection
Some days are unusual, quieter or busier than normal. Anomaly detection flags these
days so the owner knows when something unexpected happened.
Objective and Approach
The detector flags days where one of three KPIs is far from the normal value for that
day of the week. A simple global Z-score would flag every Saturday as unusual, because
Saturdays are always busier. That is a normal pattern, not an anomaly. It is more
useful to ask whether this particular Saturday was unusual next to other Saturdays.
The algorithm groups the days by day of the week, computes the mean and the standard
deviation inside each group, and scores each day as:
Z = x −µweekday
σweekday
.
Each group needs at least four observations to be scored, that is at least four of the
same weekday on record. In practice this bar only bites on a nearly empty database:
once a few months of daily data are in, every weekday already has dozens of records,
so no real day is skipped for want of history. Four points is still a low bar, though.
With that few values the standard deviation is not stable, so the scores from the very
first weeks of data are not very reliable. Raising the bar to 8 or 10 observations, or
swapping the standard deviation for the median absolute deviation, would make those
early scores more trustworthy. This is a known weak point of the current version.
The Z-score also assumes each weekday group is roughly bell-shaped around its
mean. Daily revenue is usually right-skewed, with a few busy days well above the
rest, so the score is treated as a practical ranking of unusual days rather than a strict
statistical test. The median absolute deviation mentioned above would also help here,
since it reacts less to that skew.
Severity Levels
Days where |Z| ≥2.0 are flagged, with two levels:
• Mild: 2.0 ≤|Z| < 3.0. Noticeably unusual.

• Severe: |Z| ≥3.0. Highly unusual.

5.5.9
Conversational Assistant
The chatbot is embedded in the web app as a side panel. When the owner asks a
question, a function-calling loop queries the data and generates a data-grounded answer.
Why Embed Streamlit
Rebuilding the voice input, the chart rendering and the language switching in React
would have taken weeks for no real gain. Streamlit is started with a base URL path,
Vite proxies that path, and the SPA shows the chatbot in a side panel through an
iframe. For the user it looks like one app.
Function-Calling Loop
The first version asked Gemini to write both an answer and a chart spec in one prompt.
It often made up numbers that were not in the data, gave forecasts for series the system
never forecast, and asked for charts on columns that did not exist.
The new version turns the agent into a function-calling loop. It uses the gemini-3-flash-preview
model, given a small set of tools that link directly to the chart and KPI endpoints.
Gemini calls a tool, the agent runs the matching endpoint, real data comes back, and
only then can Gemini give a final answer. The made-up answers went away, and every
reply can now be checked against the dashboards.
Tools
The agent exposes a small set of tools, each backed by a real query:
• get_revenue_forecast(days_ahead)
• get_session_forecast(days_ahead)
• get_top_members(limit)
• get_anomalies(severity)
• get_member_segment(member_id)
The assistant works on its own shared data context. This holds the three star-schema
tables it needs (the two fact tables and the member dimension) together with the six
analytics-output CSVs (member segments, loyalty scores, anomalies, peak hours by
hour, peak hours by day, and stock replenishment), nine tables in total, all written by
the same pipeline that feeds the dashboards.
There are five tools but nine tables, so not every table has its own tool yet. The
five cover the questions the owner asked most during testing: forecasts, top members,
anomalies and a member’s segment. Peak hours and stock replenishment came up less
often, so they are left in the context for now without a dedicated tool. Adding a tool is
a small change, since each one is just a thin wrapper over a query that already exists,
so the set can grow as new questions come up.

Threats to Validity
The biggest risk with the assistant is a confident wrong answer. In the first version,
during testing, the assistant once returned a detailed answer about “the forecast for
member count in July” when the system never produces such a forecast. The number was
made up entirely, but the wording sounded so natural that it almost passed unnoticed.
So I rebuilt it as a function-calling loop: the model can only answer after a tool
has returned real numbers, so every figure can be traced back to a query and checked
against the dashboards. That makes the risk smaller, but it is still possible. The model
can still word a correct number poorly or pick a less relevant tool, so the answers are
best treated as a quick first look at the data rather than a stand-in for the dashboards.

General Conclusion
Over four sprints, this project turned a year of unused activity data from Gamefy
Academy into a web application the owner now opens every day. What started as Excel
files sitting on a local drive became a working tool that reports on sales, sessions and
members, forecasts the months ahead, and answers plain questions in writing.
• Sprint 1: Preparation and Data Warehouse. Requirements, a priority
backlog, the architecture, the dimensional model and the ETL pipeline that builds
the star schema.
• Sprint 2: Authentication and Sessions. A login page and a session system
with per-user roles.
• Sprint 3: Interactive Dashboards. The backend, the three React dashboards,
the upload page and the settings page.
• Sprint 4: Forecasts, Analytics and Chatbot. The forecasting models, the
segmentation, the anomaly alerts, the Forecasts dashboard and the conversational
assistant.
The harder parts of the project were rarely the models. A narrow no-break space
hidden inside the money amounts cost about half a day before it was found. The
member segmentation started as an RFM model and was renamed once it became clear
the data held no recency information. The chatbot returned invented figures until it
was rebuilt as a function-calling loop that reads the database before it answers. The
forecasting comparison runs mostly on synthetic data, so it shows how well each model
recovers a known pattern rather than how the next year will turn out. A real measure
of future error will need a second year of data.
The structure of the system held up well. The ETL, the analytics and the web
application stayed as separate layers that talk through CSV files and a JSON API,
which kept each part easy to test and to change. The hybrid method suited the work:
GIMSI kept the design tied to the owner’s goals, and Scrum left room to absorb the
data problems that only appeared once the files were opened.
Several directions remain open. The pipeline could connect straight to the centre’s
point of sale database so the dashboards refresh on their own, and a second year of
real data would let the forecasts learn the yearly cycle and handle Ramadan correctly.
As it stands, the project already does its main job: it gives the owner one place to
see what the centre is doing and what is coming next, in numbers rather than by
instinct. Building it brought together the data engineering, the analytics and the web
development studied across the degree, and tied them to a real business that depends
on the result.
