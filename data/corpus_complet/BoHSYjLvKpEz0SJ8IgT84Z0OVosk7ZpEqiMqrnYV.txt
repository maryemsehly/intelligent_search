INTRODUCTION GÉNÉRALE
L’évolution fulgurante des technologies de l’information a bouleversé le paysage numé-
rique mondial, transformant profondément la manière dont les organisations conçoivent,
développent et exploitent les systèmes informatiques. Si cette transformation ouvre la voie
à des avancées majeures en matière de productivité, d’agilité et d’innovation, elle amplifie
en parallèle les risques de sécurité auxquels les systèmes d’information sont confrontés.
Aujourd’hui, il devient crucial d’aborder la cybersécurité non plus comme une simple
étape finale, mais comme un élément fondamental intégré dès la conception des solutions
logicielles.
Les approches classiques, qui compartimentaient les responsabilités entre dévelop-
peurs, équipes de sécurité et opérateurs, se révèlent inadaptées face aux exigences de
réactivité et de fiabilité actuelles. Dans ce contexte, la démarche DevSecOps apparaît
comme une évolution naturelle du DevOps, en intégrant les considérations de sécurité
tout au long du cycle de vie logiciel. Elle repose sur une vision collaborative et partagée,
dans laquelle chaque acteur devient responsable de la robustesse des systèmes.
C’est dans cette dynamique que s’inscrit notre Projet de Fin d’Études. L’objectif est de
concevoir et de déployer un pipeline DevSecOps qui automatise les contrôles de sécurité
à chaque étape du développement. Cette démarche permet d’identifier les vulnérabilités
en amont, de renforcer la résilience des applications et d’aligner le processus de livraison
avec les meilleures pratiques en matière de sécurité.

2.2
L’approche CI/CD
2.2.1
Définition de CI/CD
CI/CD désigne un ensemble de pratiques visant à automatiser les étapes du cycle de
vie des applications. L’intégration continue (CI) automatise les tests et les vérifications
dès qu’une modification est apportée au code. Le déploiement continu (CD) permet la
livraison rapide des changements validés vers les environnements de production.
Figure 2.4 – approche CI/CD
2.2.2
Intégration Continue (CI)
Processus d’intégration continue
Intégration Continue (CI)
L’intégration continue (CI) est un processus automatisé permettant de valider chaque
modification du code source en temps réel. Cela permet de détecter les erreurs le plus
tôt possible et d’assurer la stabilité de l’application. Le cycle d’intégration continue se
décompose en plusieurs étapes :
1. Commit de Code : Les développeurs soumettent régulièrement leurs modifications
dans un dépôt de code source partagé (par exemple, GitHub, GitLab ou Bitbucket).
Ces commits déclenchent automatiquement le pipeline CI.

2. Build Automatisé : Un serveur d’intégration continue (par exemple, Jenkins,
GitLab CI/CD, CircleCI) détecte les nouveaux commits et déclenche un processus
de build automatisé. Cette étape inclut :
— La compilation du code.
— La génération des artefacts (binaries, packages, images Docker, etc.).
— La vérification de la qualité du code.
3. Tests Automatisés : Durant le build, plusieurs types de tests sont exécutés de
manière automatisée :
— Tests unitaires (Mocha, JUnit) : validation du bon fonctionnement de chaque
composant.
— Tests d’intégration : vérification de l’interaction entre les différents modules.
— Tests de sécurité :
— Analyse de code statique (SAST) avec des outils comme SonarQube pour
détecter les vulnérabilités dans le code source.
— Analyse de composition logicielle (SCA) pour scanner les dépendances du
projet et identifier les bibliothèques vulnérables.
— Tests de sécurité dynamiques (DAST) pour exécuter des tests de pénétra-
tion automatisés sur l’application en cours d’exécution.
4. Feedback Rapide : Si des tests échouent ou si des vulnérabilités sont détectées,
les développeurs reçoivent un retour immédiat. Cette étape permet de corriger les
erreurs avant de fusionner le code dans la branche principale, garantissant ainsi la
stabilité et la sécurité de l’application.

— Analyse de Code Statique (SAST) : L’analyse statique est effectuée pour dé-
tecter les vulnérabilités dans le code source, telles que les failles XSS, les injections
SQL ou les mauvaises pratiques de sécurité.
— Analyse de Composition Logicielle (SCA) : Cette analyse permet d’identifier
les bibliothèques obsolètes ou vulnérables utilisées dans le projet, réduisant ainsi les
risques liés aux dépendances non sécurisées.
— Tests de Sécurité Dynamiques (DAST) : Les tests dynamiques sont exécutés
sur l’application en cours d’exécution pour détecter des vulnérabilités exploitables
en conditions réelles.

Déploiement Continu (CD)
Le Déploiement Continu (CD) est un processus automatisé permettant de livrer les

1. Préparation du Déploiement : Une fois les tests validés et le build généré, les ar-
tefacts (images Docker, packages, fichiers binaires, etc.) sont stockés dans un registre
sécurisé ou un espace de stockage temporaire, prêt pour le déploiement.
— Création de l’image Docker (si l’application est conteneurisée).
— Vérification des dépendances et de l’intégrité des artefacts.
— Génération de fichiers de configuration (par exemple, .env, secrets).
2. Déploiement Automatisé : Le pipeline CD déploie automatiquement les arte-
facts dans un environnement cible. Cela peut être un environnement de staging

— Déploiement sur un serveur cloud ou un serveur physique.
— Mise à jour des conteneurs Docker ou des instances virtuelles.
— Application des configurations réseau (DNS, proxy, load balancer).
3. Vérification Post-Déploiement : Après le déploiement, plusieurs vérifications

2.3
Architecture Cloud et déploiement sécurisé via
DevSecOps
L’architecture Cloud constitue un socle essentiel pour la mise en place eﬀicace d’une
stratégie DevSecOps. En effet, les trois modèles principaux de services Cloud — IaaS,
PaaS et SaaS — jouent chacun un rôle spécifique dans l’intégration de la sécurité au
sein du cycle de vie du développement logiciel.
— IaaS (Infrastructure as a Service) désigne la fourniture de ressources informa-
tiques virtuelles — comme des machines, du stockage ou des réseaux — sur demande.
Les équipes DevOps utilisent cette couche pour déployer leurs environnements de
développement et de production. L’ajout de solutions de sécurité comme Trivy (pour
scanner les images Docker) ou Checkov (pour auditer les fichiers d’infrastructure)
permet d’assurer un haut niveau de sécurité dès la phase de provisionnement.
— PaaS (Platform as a Service) met à disposition une plateforme complète de
développement et de déploiement, sans que les utilisateurs aient à gérer l’infrastruc-
ture sous-jacente. Des outils CI/CD comme GitHub Actions, GitLab CI ou Azure
DevOps s’intègrent facilement à ces plateformes pour injecter des étapes de sécurité
(tests SAST, SCA, DAST) dans la chaîne de livraison.
— SaaS (Software as a Service) désigne les applications accessibles directement via
un navigateur, souvent proposées sous forme d’abonnement. Dans ce cas, la sécurité
passe par la gestion des identités, . DevSecOps veille ici à maintenir une posture de
sécurité constante lors de chaque mise à jour du service.
En combinant ces modèles de services Cloud avec les pratiques DevSecOps, les entreprises
peuvent assurer un déploiement continu sécurisé, réduire les risques liés aux failles de
sécurité et garantir une meilleure résilience de leurs applications.

fournies directement par GitHub. Chaque exécution de workflow s’effectue dans

— Avantages : aucune maintenance, environnement propre à chaque exécu-
tion, mise à jour automatique.
— Inconvénients : ressources limitées, faible personnalisation, dépendance
à GitHub.

CONCLUSION GÉNÉRALE
À l’ère du numérique, où la rapidité de livraison et la complexité des applica-
tions ne cessent de croître, la sécurité ne peut plus être reléguée à une étape
secondaire. Elle doit être pensée comme une composante essentielle, intégrée
dès les premières phases de développement. Le modèle DevSecOps incarne
parfaitement cette vision moderne de la sécurité, en favorisant une approche
proactive, automatisée et continue.
Au cours de mon Projet de Fin d’Études , j’ai eu l’opportunité de mettre en
œuvre un pipeline DevSecOps complet, combinant des outils d’analyse statique
(SAST), d’analyse dynamique (DAST), et de contrôle des dépendances (SCA),
tout en respectant les principes de l’intégration et du déploiement continus. Ce
pipeline nous a permis de détecter les vulnérabilités à différents niveaux, de
renforcer l’infrastructure conteneurisée .
Ce projet a représenté bien plus qu’une simple réalisation technique. Il a permis
de mettre en pratique des compétences transversales en développement, en
sécurité informatique, en gestion de projet et en automatisation. Il a aussi mis
en lumière l’importance d’une culture collaborative entre développeurs, devops
,experts sécurité.
En guise de perspective, plusieurs pistes d’amélioration peuvent être envisa-
gées :
— L’adoption de pratiques MLOps pour automatiser le cycle de vie des mo-
dèles IA : entraînement, validation, déploiement et supervision continue,
— L’automatisation complète du déploiement via des orchestrateurs comme
Kubernetes.
En conclusion, cette expérience a démontré qu’il est possible de concilier ,
performance et sécurité, à condition d’adopter une démarche structurée et de
s’appuyer sur les bons outils. DevSecOps n’est pas qu’un ensemble de techno-
logies, c’est avant tout un changement de culture.
