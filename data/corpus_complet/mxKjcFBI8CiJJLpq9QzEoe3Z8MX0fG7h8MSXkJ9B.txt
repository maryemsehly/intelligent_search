1.8. Global Architecture 
SECA is proposing a solution to the absence of structured marina energy stations 
with the installation of connected energy stations that can be monitored and 
controlled wirelessly. 
Each connected energy station has its own metering modules that measure 
consumption for electricity and water separately. Metered data is captured by the 
central controller (i.e., motherboard), which will compile metered data into a 
totalized data set and manage the activation or deactivation of energy and water 
distribution. 
Totalized data will then be sent through a brokered communications framework 
to the Marina Server, which is the core component of the whole solution. The 
Marina Server will communicate with each of the connected energy stations, 
centralize the collected data sets, and provide a secure database of consumption 
and operational records for each connected energy station. Therefore, the Marina 
Server will not only act as the communications hub but will also serve as a means 
to back up and synchronized the connected energy stations' data and associated 
management data. 
The Marina Server will provide marina management and end-users access to the 
information stored at the Marina Server through their respective applications. 
A web-based application will be supplied to marina employees for monitoring 
stations, managing users, managing subscriptions, and issuing commands or 
synchronizing data with the connected energy stations using the platform's API. 
Clients of the Marina will be able  ‎ماuse a mobile application where they  ‎صقview 
their current power consumption at the power station assigned to them by Marina 
management, as well as their active subscriptions and available credit. Clients will 
be able to see their current energy or financial consumption associated with the 
station and overall view of their use and balance.

2.1. Specification 
Upon arriving at the marina station, the boat owner simply flashes their RFID card 
at the reader. The RFID module receives the unique identification number of the 
card and sends this information to the station controller, which commences the 
authorization process. 
The initial phase involves checking if  ‎عطcard belongs to a registered user. The 
station then searches its database of registered users for a record corresponding 
to the received  ‎  ١١ .ثانا‎دهmatching record  ‎كاfound,  ‎عطsystem rejects access, 
generating an 'unknown card detected' event which  ‎مقalso be 5601 10 the marina 
administration server to alert the marina staff. 
If the card is a recognized one, the system retrieves the associated user profile, 
and then proceeds to the second phase of verification. The system verifies that 
the subscription is active. It checks if  ‎عطcurrent date and time are between the 
start date and expiration date in the user's database record. If the subscription 
has expired, the user  ‎كاrefused access, and an 'expired subscription' event is 
generated. 
Once the subscription is validated, the station checks the permissions associated 
with the user. Depending on the subscription plan, the user might have access to 
electricity, water and gas. The system then determines which resources should be 
available for the user to consume by referring to these permissions. 
Before enabling any resource, the system checks if the user already has an active 
session running. If no active session is found, the card scan is registered as an 
attempt to start a new session. The system creates a new session record 
comprising the user identifier, the station identifier, the start time of the session 
and the starting values of the consumption counters which have been read by the 
installed sensors. 
Once the session has been initiated, the station enables solely those resources 
the user is permitted to consume. An active session message can simultaneously

be sent to the marina administration server allowing the marina system to monitor 
its active users and the usage of resources at the time. 
Throughout the duration of the session, the system continuously receives the 
measurements made by the sensors of the resources installed at the station. 
Depending on the type of resource, the measurements are recorded in kilowatt 
hours for electricity, liters for water and cubic meters for gas. These measurements 
can be sent to the marina administration system at intervals, or after the end of a 
session, including the user and station identifiers, the type of resource and the 
measurements themselves, i.e. The values and time stamps. 
The system can also provide with pre-determined consumption limits. If à limit has 
been reached by a user the respective resource can be turned off automatically 
and a 'limit reached' event may be generated. 
The session continues to be active until the boat owner flashes the RFID card at 
the reader again. This action is immediately recognized by the station as the 
system notices the presence of an active session corresponding to that user. Thus 
the system does not start a new session but rather considers this event as an 
indication that the boat owner is terminating the session. 
The system takes note of the final measurements of the sensors and calculates the 
consumed amounts by subtracting the initial sensor values that were saved when 
the session was started from the final values.

prepared that include among others the user and station identifier, the time 
interval for which the session was active, and the amounts of the resources 
consumed by the user. 
The session data is stored and it can also be transmitted to the marina

3.1.4.1 Objective and Measurement Approach 
The objective is to determine the volume of water consumed, typically expressed

In practical systems, water consumption is measured by: 
e

e

In embedded systems, a common and efficient approach is to use pulse-based

3.1.4.2. Principle of Operation 
The sensor used in this project operates using a turbine and Hall-effect 
mechanism. 
When water flows through the sensor: 
e 
À small internal turbine rotates 
e 
Each rotation generates electrical pulses via a Hall-effect sensor 
The key idea is:

3.1.4.3. Pulse-to-Volume Conversion 
To obtain water consumption, a conversion factor must be applied. 
For typical flow sensors of this type: 
1 liter = 450 pulses 
This means that: 
Volume (L) = Pulse count / 450 
The sensor may also provide a relation for flow rate: 
Flow rate (L/min) = pulses per second / 7.5 
This conversion is essential, as it transforms raw electrical signals into meaningful

3.2.1. Presentation of the Clean Architecture 
Clean Architecture is a way of writing code that separates the system into clear 
layers. The main idea is simple: the business rules sit at the center, and everything 
else depends on them. This means the code that decides what the system does 
never depends on the code that decides how it connects to a sensor or how it 
sends a message over Wi-Fi.

3.2.2. Domain Layer 
Domain: The core of the system.  ١١lays  ‎صthe center of Clean Architecture and 
comprises all elements of business logic. This layer doesn't know about the ESP32, 
the MQTT broker, the RFID reader and any other technology. Even if we could 
remove all hardware and change the Infrastructure layer completely, the domain 
layer wouldn't be touched. The layer contains three kinds of elements: 
Entities: Here we show the major business objects. In the system, major business 
objects are Subscriber, Subscription, Session, Tariff. An entity is identified by its

Interfaces (Abstract Contracts): These are C++ pure virtual classes which specify 
what the system requires, without specifying how. This is the tool that the 
Dependency Rule forces us to use.

Conclusion 
This project addressed an explicit operational issue of the management of 
subscriber access and resources consumed in a marina. The objective was to 
design and prototype an autonomous station that, by tapping an RFID card, could 
verify a subscriber, and keep a real-time trace of the electricity and water 
consumed by the subscriber; then send this data to a central server using the 
MQTT protocol. 
The solution designed relies on an ESP32 microcontroller as it offers an integrated 
Wi-Fi capability and can be connected to the SMC51 488 RFID reader, the PZEM- 
0041 energy meter and the YF-S201C water flow sensor simultaneously. The 
hardware choice was based on criteria of cost, compatibility and reliability. 
In the software part, the firmware of the device was developed following Clean 
Architecture principles. The triple-layer (Domain, Business and Infrastructure) 
design guarantees a total independence between the business logic and the 
technical considerations. Through the use of interfaces, the notion of Inversion of 
Control ensures the business logic is completely isolated from concrete storage, 
communication or sensing implementation, paving the way for easier evolution of 
the hardware configuration. 
The communication protocol chose is MQTT and the Mosquitto Eclipse broker was 
used for this. Messages between the device and the server are defined with a 
specific structure based on JSON in order to manage subscriber's synchronization, 
authentication orders, and consumed resources' records. 
A full stack simulator was designed to enable the system validation without a 
production server and a repeated manipulation of the prototype. This application 
developed using React, TypeScript, Hono, tRPC and MySQL served to test and 
validate the full system during  ‎عطintegration tests with  ‎عطprototype. 
The V-model development methodology used provides a clear structure in the 
different phases of the project (requirements, design, implementation, testing), 
and allows an easy traceability between initial goals and end product. 
47

Limits and Perspectives 
Because this project was conducted in the timeframe allowed for a final year 
project, unit testing has not been implemented systematically along with fully 
realizing the water consumption. However the architecture developed enables unit 
test easily since the Domain layer does not contain external dependency. The 
abstraction through interfaces also facilitates the mocking for tests of the business 
and domain layer. Further development should include completing the unit testing 
framework. 
Other features are possible with this project in order to evolve it to a product 
version. Some include: 
** Security: implement TLS communication for MQTT and provide password 
authentication for the broker. 
** Offline reliability: save data locally if the connectivity fails and send them 
back to the server later. 
** Over-the-air firmware updates: use MQTT to push new firmware version 
to devices. 
** Management of different resources with various costs. 
This project demonstrates that it is possible to implement an embedded system 
whose purpose is to manage the operational aspect of a marina resource using 
modern development principles. The prototype presented proves the whole 
workflow between the user action and its effect on resource billing.
