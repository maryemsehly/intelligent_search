ABSTRACT
The EcoSort project introduces an innovative AI-IoT-based waste management system
designed to automate waste collection and sorting, improve the cleanliness of spaces, and
streamline waste handling for governmental operations. The system integrates autonomous
robots, named WasteBots, equipped with advanced robotics and AI-powered computer vi-
sion models to detect, classify, pick up, and deposit waste with precision. The integrated
robust IoT platform ensures seamless communication and data exchange among devices,
while the EcoSort WebApp provides intuitive interfaces for real-time system monitoring and
control. Key challenges, including accurate waste sorting, hardware integration, efficient
navigation, and resource optimization, were effectively addressed through advanced engi-
neering and adaptive problem-solving, resulting in a reliable, efficient, and scalable waste
management solution. The EcoSort project underscores the revolutionary potential of AI,
IoT, and robotics technologies, revolutionizing sustainable waste management solutions.

Internet of Things:
The Internet of Things (IoT) [11] refers to the interconnected ecosystem of physical devices
embedded with sensors, software, and network connectivity that enables data exchange with
cloud platforms and between the devices themselves. The term Internet of Things was for-
mally introduced in 1999 by Kevin Ashton at Massachusetts Institute of Technology
MIT [12] to describe a system where physical objects, embedded with sensors and identi-
fiers, could be interconnected through networked infrastructure. IoT devices, also known as
connected devices or smart objects, are widely used nowadays. They range from sim-
ple applications (e.g., wearables, smart security cameras, RFID tags) to complex ones (e.g.,
smart cities, transportation systems, agritech, industrial machinery). In 2024, the number
of active IoT devices worldwide was estimated to be 16.7 billion. Market analysis predicts
that this figure will expand to 29.4 billion devices by 2030, at a compound annual growth
rate (CAGR) of 9.6% [13]. This sustained growth trajectory is primarily empowered by

three key technological advancements:
• 5G Technology: The widespread use and deployment of 5G networks provide high

• Cloud and Edge Computing: Cloud computing offers remote and scalable data
storage and processing, while edge computing handles data processing near the source
or the IoT node. This minimizes latency and improves the performance of IoT systems,
especially for real-time IoT applications.
• AI: The integration of AI-enabled IoT solutions optimizes data processing, predictive

The Internet of Things relies on diverse protocols and technologies to enable seamless
communication, data exchange, and device functionality. Protocols such as MQTT (Mes-

technologies such as RFID (Radio Frequency Identification), BLE (Bluetooth Low Energy),
NB-IoT (Narrow-band IoT), and LoRaWAN (Long range Wide-Area Network) provide con-
nectivity solutions tailored to specific needs. These needs vary depending on the IoT system
or the IoT application requirements. For example, some IoT applications need short-range
communication; others need wide-area coverage. These technologies and protocols together
form the foundation of IoT ecosystems, ensuring interoperability, scalability, and reliability
across different use cases. IoT brings several advantages that enhance efficiency and drive
technological advancement. The following are the main IoT benefits:
• Connectivity: IoT devices are linked to the internet or local networks, enabling
seamless communication with central systems or other connected devices. This con-

• Data Collection and Analysis: The integration of IoT facilitates the collection of

big data analytics and AI models.
• Remote Monitoring and Management: Thanks to IoT technologies, devices can

• Scalability: IoT architecture can be easily scaled either by the addition or the removal

insufficient for a secure IoT system or application. Instead of that, IoT devices, IoT
networks, and IoT cloud platforms – all of them – must be well secured. Additionally,
IoT devices collect and handle sensitive and personal data, such as behavior, health

3.2.2
Solution Architecture
The architecture of the EcoSort system explains how components work and interact to-
gether to provide a robust waste management application. To start with, WasteBots, the
autonomous robots, publish the waste data to the AWS IoT Core platform after the collec-
tion and sorting process. At the core of the system, a Django-based backend server acts
as the central unit, facilitating communication between the different system’s components.
It is a subscriber to the AWS cloud platform. The server uses multi-threading features to
listen for new updates coming from the cloud platform and run other tasks simultaneously.
After receiving new data, the server interacts with the MySQL database, executing CRUD
(Create, Read, Update, Delete) queries to store and manage waste data efficiently. End-users
interact with the system through a React Web Application, which communicates with
the Django web server to display real-time data of collected waste, users, WasteBins, and
WasteBots. The web application provides other features, including component management
and control.

Evaluation Metrics
To measure the performance of the YOLO model, the following set of metrics is employed:
• Precision: It is a metric used to evaluate the performance of a classification model.
It answers the question, ”Of all instances predicted as positive, how many are
actually positive?” The precision score ranges from 0 to 1, where a higher score
means higher accuracy, indicating a lower rate of false positives.
Precision =
TP
TP + FP
Where:
TP: True Positive (The model correctly predicts the positive class.)
TN: False Negatives (The model correctly predicts the negative class.)
FP: False Positives (The model incorrectly predicts the positive class.)
FN: False Negatives (The model incorrectly predicts the negative class.)

• Recall: It is a metric used to measure the model’s ability to detect all actual positive
instances. It answers the question, ”Of all actual positives, how many did the
model correctly identify?”
Recall =
TP
TP + FN
• F1 Score: It is a key metric in machine learning that balances precision and recall
into a single value. A high-precision model reduces false positives but may miss true
positives (lower recall), whereas a high-recall model captures most positives but may
include more false alarms (lower precision). To solve this problem, the F1 Score comes
to harmonize this trade-off by combining both metrics, introduced in the following
formula:
F1 = 2 × Precision × Recall
Precision + Recall
• mAP50 [38]: It stands for mean average precision calculated at an intersection over
union (IoU) threshold of 0.50. It is a standard evaluation metric for object detection
models (e.g., YOLO) that measures the average detection accuracy across all classes
when a predicted bounding box is considered correct if it overlaps with the ground
truth bounding box by at least 50% IoU.
• mAP50-95 [38]: The average of the mean average precision over a range of IoU thresh-
olds from 0.50 to 0.95. Providing a comprehensive view of the model’s performance
across different levels of detection difficulty.

4.3.6
Sprint 2: YOLO Fine-tuning
YOLO (You Only Look Once) is a real-time object detection algorithm. Unlike traditional
methods that rely on multiple and complex pipelines, it processes an entire image in a single
forward pass through a neural network architecture. YOLO divides the image into a grid and
then predicts bounding boxes and class probabilities as well, enabling real-time computer
vision applications while maintaining a strong accuracy. It is widely implemented in various
domains, such as healthcare, manufacturing, autonomous driving, and waste management.
The most well-known and powerful YOLO models are developed by Ultralytics, which is a
leading company specializing in computer vision and machine learning. It provides open-
source solutions and products, such as YOLOv11, YOLOv8, and YOLOv5 [50]. Among those
models, which is the best choice for WasteBot, considering all the hardware and software
constraints? The answer will be presented in the next section.
4.3.6.1
Model Choice
Ultralytics offers a suite of high-performance object models, each with distinct specifi-
cations and advantages for real-time detection and classification. The optimal choice that
aligns with WasteBot depends on several constraints related to the Raspberry Pi board:
• CPU/GPU: The Raspberry Pi 4B does not come with a dedicated GPU for com-
puter vision tasks, yet its built-in GPU, the Broadcom VideoCore VI, operating with
the ARM Cortex-A72, can handle lightweight models, enabling reliable basic AI capa-
bilities.
• Memory: The Raspberry Pi 4B comes with 1, 2, 4, or 8GB of RAM; the integration
of lightweight models can be practical with 4 and 8GB versions, ensuring simultaneous
use of the RAM by other tasks, such as OS tasks.
• Energy: The WasteBot relies on a battery as a power supply. Although computer vi-
sion tasks are energy-consuming, integrating lightweight models can be an appropriate

4.3.8.3
Inverse Kinematics
Inverse Kinematics (IK) is the process of calculating the joint parameters (angles, posi-
tions, or displacements) of an articulated system to properly position its end effector (e.g.,
hand, gripper) at a desired target location and orientation. It solves the opposite problem
of Forward Kinematics, which determines end-effector pose from given joint angles.
The joint angles calculation of a 4-DOF robotic arm requires solving trigonometric equa-
tions, mapping the end effector pose to the input point coordinates (x, y, z). Since a 4-DOF
arm requires 4 angle values (base θ1, shoulder θ2, elbow θ3, wrist θ4), the mathematical
problem will be composed of 4 equations to solve:
1. Base angle θ1: It determines how much the robotic arm needs to rotate around its
vertical axis (Z), aligning with the target point (x, y, z) in the horizontal (x, y) plane.
The base angle is calculated using the following formula:
θ1 = atan2(y, x)

4.3.8.4
Picking Up Waste
Studying and defining theoretical Inverse Kinematics formulas is crucial; however, in the
actual WasteBot Arm, the IK is only used to calculate the base angle θ1 while keeping all
other joint angles (shoulder θ2, elbow θ3, wrist θ4) fixed in an optimized, preconfigured ”mid-
reach” pose. Those angles are carefully calibrated to provide maximum useful workspace
coverage while maintaining a more stable and effective picking solution, which is particularly
effective for repetitive pick-and-place operations of approximately equal waste sizes, such as
papers, plastic bottles, metal cans, and glass pieces. This approach offers a set of advantages,
keeping a robust arm movement solution, following θ1 IK formula, θ1 = atan2(y, x):
• Simplified Control: Single-axis adjustment reduces system complexity.
• Stability: Preconfigured θ2/θ3/θ4 reduce error propagation.
• Computational Efficiency: Eliminates iterative IK calculations.
• Operational Reliability: Consistent performance in repetitive tasks.

ArUco Markers
An ArUco (Augmented Reality University of Cordoba) marker [52] is a synthetic square
marker composed of a wide black border and an inner binary matrix for unique identification.
The black border is a thick outer frame that enables fast and effective detection in images
despite unstable environmental conditions. On the other hand, the binary matrix is an inner
grid that encodes a unique identifier (ID) using binary patterns. The marker size determines
the size of the internal matrix (e.g., a marker size of 4x4 is composed of 16 bits). ArUco
markers are implemented in various fields, particularly in robotics, enabling efficient and
robust computer vision tasks such as navigation, pose estimation, and unique identification.

5.3

5.3.1
Multi-threading and Real-time Communication
Multithreading is a common technique that enables managing multiple simultaneous tasks,
ensuring real-time interactions. The initial challenge was the MQTT listening issue. The
server must handle the backend logic simultaneously with the MQTT listening task, ensuring
that real-time data updates are received from WasteBots. Although the Django framework
supports multithreading, it was set by default to handle tasks sequentially. Addressing this
incompatibility issue, the Python threading library was imported and integrated, enabling
the handling of tasks simultaneously in separate threads. The second challenge was the dupli-
cation issue. The multi-threading library solved the first problem perfectly, yet threads were
112


===== PAGE 130 =====

Chapter 5. Evaluation
processed twice, highlighting a duplication problem. After further research, it became clear
that the WSGI, defined in the subsection 4.2.4.4, is a synchronous technique that Django
enables by default, although multithreading requires an asynchronous approach to work
properly. To address this issue, the ASGI defined in the subsection 4.2.4.4, was enabled
alongside the corresponding configuration in asgi.py and app.py Django files, deprecating
WSGI since ASGI supports both asynchronous and synchronous approaches.
The third
challenge was the incompatibility between the ASGI approach and the standard command
to run the Django server; python manage.py runserver, as it does not support an asyn-
chronous approach. To resolve this problem, the following command is used instead: uvicorn
backend server.asgi:application --host [ ] --port [ ].
It is based on Uvicorn,
which is a lightning-fast ASGI server designed for asynchronous web applications. Through-
out these challenges, the key lessons learned emphasize the importance of analyzing project
use cases early in the development cycle to identify where the multi-threading requirements
reside. Furthermore, the continuous learning and skill development in multithreading are
highly required, as it is one of the most crucial features required in numerous projects.
5.3.2
Dashboard Real-time Updates
The dashboard represents the project user interface that allows for interactions between
users and EcoSort functionalities, ensuring real-time monitoring, control, and updates. The
challenge faced in the UI real-time update is the improper connection between the backend
and the frontend. To clarify, the backend server receives published data from WasteBot in
real time perfectly, but nothing is shown and updated in the dashboard. After debugging, the
problem was found to lie in the HTTP approach. Basic HTTP protocol relies on the client
to initiate connections with the server and wait for responses to the requests sent. In other
words, HTTP communications are initiated only by the client, which is not the correct case
to handle real-time updates. Instead, the backend server needs to send published data from
WasteBot without a client request because update times are not predicted and out of the
113


===== PAGE 131 =====

Chapter 5. Evaluation
front-end logic scope. To address this problem, the WebSocket protocol was selected first
thanks to its ability to ensure a continuous full-duplex connection between the server and
the client without time constraints, ensuring real-time updates. Although the WebSocket
protocol is powerful and consistent, it is not the ideal choice in this case due to its high
resource consumption and the unnecessary use of a full-duplex connection. To handle this
matter, Server-Sent Events (SSE) is selected, which is an HTTP-based, lightweight, and one-
way communication protocol designed for half-duplex real-time scenarios from the server to
the client. This makes it an ideal choice to handle real-time updates, maintaining lower
complexity and resource consumption efficiency. Lessons learned involve how to properly
define the case requirements early, ensuring a much more optimized and clearer development
cycle, improving the overall project performance.
5.3.3
Locating and Navigation to Bin
After detecting, classifying, and picking waste, WasteBot locates and navigates to the
corresponding bin based on the waste type. The challenge faced in realizing this task is
the inability to recognize the bin’s ArUco marker, leading to an infinite loop of searching
(360° rotation). Following the debugging process, the problem was occurring in time inter-
vals between tasks. The rapid 360° rotation movement prevents WasteBot from detecting
the marker. More accurately, the rapid rotation distorts the captured image and therefore
distorts the marker matrix. To resolve this issue, small stopping delays are included dur-
ing the 360° searching movement, leveraging the Python time library, precisely the sleep()
function, ensuring WasteBot takes a sufficient time to analyze objects, specifically AruCo
markers inside the frame captured. The lesson learned is how much the proper integration
of delays can improve the system functionalities, preventing the mismanagement of tasks,
high resource consumption, and energy waste. Future work could focus on the integration of
mapping techniques such as the SLAM (Simultaneous Localization and Mapping) technique,
which enables robots to build a map of an unknown environment while simultaneously de-

a more advanced and flexible way of automatically identifying varying working spaces like
various urban green park surfaces, alongside proper detection and navigation to correct bins.
5.3.4
Robotic Arm
The robotic arm represents the robotic part of WasteBot. It is selected based on a set
of requirements, namely force, size, and weight, while ensuring proper integration into the
robot’s design. The initial challenge was choosing the right arm. The first one selected,
although it is lightweight and cost-effective, was unsuitable due to its lack of solidity and
accuracy, resulting in difficulties achieving accurate movement and picking. Addressing this
issue, a more robust and advanced arm was selected. It provides a more suitable design and
higher torque, ensuring a proper and reliable interaction with real-world objects. However,
a second challenge emerged during the integration of this second robotic arm due to the
incompatible arm base that prevents the direct assembly with the robot chassis. To resolve
this problem, an intermediary 3D-printed piece was designed and implemented in between.
This piece not only ensured a proper hardware integration and assembling process but also
minimized vibrations during arm movement, enhancing overall system stability and reliabil-
ity. Key lessons learned included the importance of carefully and holistically studying the
required project parts before the integration process, considering the pieces’ characteristics
and specifications. Additionally, enhancing skills in 3D designing is needed since it solves
various hardware incompatibilities. Moving forward, future work could focus on selecting a
longer arm, balancing between the length, weight, and size. This will offer a wider capability
in dealing with a wider variety of waste shapes, sizes, and weights.
5.3.5
AruCo Reading and YOLO Object Detection
ArUco marker reading and YOLO object detection introduce the computer vision side of
the project, achieving seamless and efficient object recognition and tracking. The primary

challenge involved managing access to the camera hardware, which was required by the cv2
Python library for ArUco processing and the Picam2 Python library for YOLO object de-
tection. This conflict occurred because both libraries attempted to access the camera as a
shared resource, resulting in potential resource conflicts and frame-capturing failures. To
resolve this issue, a sequential resource management strategy was implemented. After com-
pleting each task, the respective library released the camera hardware, using .release() for
the cv2 instance and .close() for the Picam2 instance. Since the two tasks are executed
sequentially, there is no need to implement a synchronization approach like the mutex and
semaphore techniques. Therefore, implementing proper resource management between tasks
is sufficient to ensure safe and seamless use of the shared camera. Key lessons learned em-
phasize the importance of learning and applying hardware resource management techniques
since it is crucial for safe and real-time projects.

Camera Assembling and Frame Capturing

position, considering the waste position in front of the robot and the camera’s field of view.
This ensures stability and accuracy across different waste sizes and shapes for classification
while maintaining effective ArUco marker detection and tracking. The camera was cali-
brated to an optimal angle, providing a clear and undistorted view. The second challenge
consists of properly attaching the camera to the camera holder. The chosen camera cannot
be directly attached to the holder due to hardware measurement incompatibility. To resolve
this issue, a 3D-printed intermediary piece was designed, ensuring a seamless and robust
hardware assembly. Key lessons learned emphasize the need for continuous improvement of

plementarily validate the software functionalities, and how it can contribute to better system

6.2
Limitation and Future Work
The EcoSort system’s modular design provides a robust foundation for future enhance-
ments, paving the way for more sophisticated and capable waste management solutions.
Several potential areas for future work have been identified to improve the system’s func-
tionality, scalability, and reliability:
• Increased Robot Size and Capacity: The current EcoSort robots are limited in
size, restricting their ability to navigate complex terrains and handle larger waste
volumes. Future designs could involve scaling up the robots to enhance stability and
adaptability, making them more effective for real-world waste management operations.
• Enhanced Computational Hardware: EcoSort’s current hardware is sufficient for
medium-range AI and IoT tasks but struggles with high-complexity computations,
limiting responsiveness and scalability. Upgrading to advanced hardware, such as the
NVIDIA Jetson series, would significantly enhance the system’s processing power, al-
lowing for more advanced AI models’ integration and complex IoT workflows with
minimal latency.
• High-Resolution Camera and Expanded AI Model: EcoSort performs effec-
tively in detecting and classifying waste, but its capabilities can be further enhanced
by integrating a higher resolution camera.
This upgrade would improve detection
accuracy. Additionally, expanding the YOLO model to recognize more detailed cate-
gories, such as wet waste, dry waste, cardboard, and chemical waste, would enhance
the system’s sorting capabilities.
• SLAM and Mapping Integration: WasteBot can properly move and identify ap-
propriate bins, leveraging the ultrasonic sensor and ArUco markers. However, integrat-

===== PAGE 138 =====

ing a more advanced mapping technology, such as SLAM (Simultaneous Localization
and Mapping), will perform better in localizing and mapping processes. Technically,
SLAM is a computational technique that enables a robot or autonomous system to con-
struct a map of an unknown environment while simultaneously estimating its position
within that map. It relies on sensor data (e.g., LiDAR) and algorithms like Graph-
SLAM. By integrating SLAM, WasteBot can autonomously move through complex
and dynamic spaces, providing a robust solution to adapt to unknown environments
and conditions.
• Integration of Smart Waste Bins: EcoSort contains traditional waste bins, each
identified by a unique ID involved in its ArUco marker.
The integration of smart
WasteBins will improve the system performance, leveraging more IoT sensors for real-
time monitoring of WasteBins’ fill levels, temperature, and humidity. Smart WasteBins
enable automation, optimize collection routes, and prevent overflow and fire incidents.
Additionally, they will enable predictive analytics and dynamic resource allocation.
The integration of smart bins as new IoT nodes alongside WasteBots will ensure a
more seamless, reliable, and efficient data-driven waste sorting ecosystem.
